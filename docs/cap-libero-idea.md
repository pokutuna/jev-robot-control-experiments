# 応用編1 最終課題 計画: LIBERO で System 1 モデルをロボット操作と Code as Policies に使う

応用編1 の最終課題 (締切 2026-11-02 10:00) の計画。課題の要件は [lecture99_final_SUMMARY.md](../lectures/advanced1/99/lecture99_final_SUMMARY.md) にある。Microduck を使う別案は [sock-retrieval-plan.md](sock-retrieval-plan.md) にある。

## 1. 題材と問い

Franka Panda がシミュレータ (LIBERO) 上で卓上の物体を操作する。System 1 モデルの Jev に、ロボットの次の動作を選ばせる方式と、LLM が書いた制御コード (Code as Policies、以下 CaP) の中の条件判定を任せる方式を実装し、成功率と失敗の仕方を比べる。画像を入力できる版として Jev 1.14 Preview を使う。

答えたい問いは次の 2 つである。

1. Jev にロボットの次の動作を選ばせるとき、物体の名前と位置の真値を JSON で渡す場合と、カメラ画像だけを渡す場合で、成功率と失敗の仕方はどう変わるか。選択肢の粒度 (primitive か移動方向か) と、意図と動作を分けて 2 回聞く構成は、結果をどう変えるか。
2. CaP の生成コードの中の条件判定を Jev の画像判定に任せると、判定のないコードに比べて、把持の失敗などからどこまで回復できるか。真値から計算した幾何判定にどこまで迫れるか。

問い 1 だけで十分な結果が出れば、それを最小構成として完成とし、問い 2 の実装は省く。課題の合格条件は「ロボットがタスクを実行している動画」なので、最小構成でも Jev がロボットを動かす部分 (後述の C) は必要になる。

## 2. 背景

### Code as Policies

CaP (Liang ら、arXiv 2209.07753) は、使える API と数個の例を LLM に与え、自然言語の指示から制御プログラムを生成させる手法である。LLM が書くコードは、知覚 API で物体の位置を取り、制御 primitive の API に引数を渡す。能力は渡した API の範囲に限られ、知覚 API で書けない概念 (「空いている」「倒れている」「中に入っている」) は扱えない。

講義では、基礎編第 1 回でロボットポリシーの 3 分類 (E2E、E2E 階層型、Code as Policies) の一つとして紹介され、例として CaP-X (Fu ら、arXiv 2603.22435) の CaP-Agent0 が挙がった。

### Jev

**Jev** は TypeSafe AI が 2026-09-15 に公開した System 1 モデルである。状態と型付きの問いを受け取り、型付きの答えと確率、確信度を返す。文章もコードも生成しない。問いの型は次の 4 つ。

- Choice: 最大 255 個の選択肢から選ぶ
- Score: 数値で採点する
- Noul: 真である確率を返す
- Box: 画像中の物体の矩形を返す (1.14 で実験的に追加)

レイテンシは 70〜500 ms、料金は入力 100 万トークンあたり $0.042 で出力は無料。公式の入力はテキストだけだが、ヘッダ `TypeSafe-Danger-Zone-Images: true` を付けると画像 (PNG/JPEG、一辺 280〜1568 px) を受け付ける。算術や数え上げは苦手とされる。SDK は `typesafe_sdk`。

### Jev をロボットに使った調査の結果

第三者の調査レポート「System 1 モデルによるロボット制御」(https://claude.ai/artifact/U4YPf3bPJUhKo4FtsLR3Gm) は、Jev は入力に含まれる情報から選ぶ評価には強く、入力にない結果を見積もる予測には弱いとまとめている。根拠は次の結果である。

- 積み木の課題で、トルクを直接選ばせると 0/20 だった。スキルを選ばせると 9/20 で、手書きの制御器の 8/20 と同程度だった。初めて見る指示では 22/40 で、手書きの制御器の 3/40 を上回った。
- ALFWorld で、各選択肢の先読みの結果を入力に足すと、解けたゲームが 134 本中 42 本から 116 本に増えた。
- 同じ入力を繰り返し送ると、Choice の答えが 12% の割合で反転した。

同レポートには、Jev 系の画像モデル (JEV-27B-VL) で二値判定をして pick and place をした例もあり、成功率は 75% で、失敗はすべて把持位置の 3.0〜3.7 cm のずれだった。

### 先行事例

Jev でロボットを動かした公開事例はいくつかある。どれも物体の情報をテキストか JSON で渡しているか、入力形式を確認できていない。LLM が書いたコードの述語として Jev を使った例は見つかっていない。CaP の後続研究をまとめた第三者のサーベイ資料 (https://claude.ai/artifact/SqMM6HbtkAKE1cWcHHs1ww) も、Jev を CaP と組み合わせた公開例はないとしている。

| 先行事例 | Jev の役割 | このプロジェクトとの違い |
|---|---|---|
| Dmytro Hrybov の投稿 (2026-09-18) | MuJoCo のアームで、意図 (掴む、運ぶ、離す) を選ぶ呼び出しと、x/y/z 移動と指の指令を選ぶ呼び出しに分ける。入力は簡略化した幾何と接触のテキスト。2 呼び出しで約 3.2 Hz | 画像入力と比べる |
| Isaac Sin の投稿 (2026-09-18) | MuJoCo のアームで、環境の状態を JSON で渡し、`hover / descend / grasp / lift / place` から信頼度付きで選ばせる。1 判断約 150 ms。シーンに対応づけられないタスクは拒否する | 画像入力と比べる |
| lykycy123/RoboJEV | Franka で意図を選び、続いて XYZ とグリッパの値を選ぶ | 構成は C2 の 2 段階版とほぼ同じ。入力形式による違いを測る |
| Dimweaker/jev-libero | LIBERO の電子レンジと引き出しの課題で、物理シミュレーションで事前に確かめた候補から選ぶ | 候補を事前に検証しない |
| openroboto-ai/jev-robot-control | xArm7 で Jev と GPT のコストと時間を比べる | 成功率と失敗の仕方を比べる |
| JevHarness (NanoJev の作者) | LLM にタスク専用の Jev 判断ハーネスを組ませ、報酬と実行トレースで改良する | ロボットでの定量評価はない |

2 つの投稿では、物体の識別は Jev ではなくシミュレータが行っている。物体の名前と位置は真値として状態に入っており、Jev はタスク指示の語をその名前に対応づけるだけでよい。状態をテキストにする具体的な形式は、投稿の本文には載っていない。

### CaP の実装パターンの分類

CaP の後続研究は、上記のサーベイ資料にならい 2 つの軸で分類する。資料が引く論文の数値は原論文で確認していないので、レポートで使う前に確認する。

1 つ目の軸は、生成コードが制御のどの層を担うかである。

- **API の組合せ**: 人が作った primitive をコードから呼ぶ。LLM はタスクの手順と引数を決め、軌道や低レベル制御は API が担う。CaP、ProgPrompt (arXiv 2209.11302)、ChatGPT for Robotics (arXiv 2306.17582)、CaP-X
- **中間表現**: コードが価値マップ、コスト関数、制約、報酬を書き、軌道は最適化器やモーションプランナが解く。VoxPoser (arXiv 2307.05973)、ReKep (arXiv 2409.01652)、Language to Rewards (arXiv 2306.08647)、Code-as-Monitor (arXiv 2412.04455)
- **VLA との組合せ**: 手順の流れと解析的な primitive をコードが担い、把持など接触の多い部分を VLA に任せる。Harness VLA (arXiv 2607.08448) は LIBERO-Pro で VLA をリトライ可能な primitive として扱っている

2 つ目の軸は、生成コードをどう改善するかである。Jena ら (2026、arXiv 2608.01851) のサーベイは、実行結果のフィードバック、タスクをまたぐ記憶、複数候補の探索の有無で 5 段階に分けている。

1. ゼロショット生成: 一度書いて実行し、失敗はそのまま (CaP、ProgPrompt、VoxPoser)
2. タスク内での修正: 実行結果を見て書き直すが、修正はタスクが終わると捨てる (Inner Monologue、REFLECT、Code-as-Monitor)
3. スキルの蓄積: 検証したコードを保存し、別のタスクで再利用する (Voyager、DROC)
4. 進化的探索: 複数の候補を実行で評価し、よいものを変異させる (CaP-X、RoboEvolve)
5. 全部入りの閉ループ: フィードバック、記憶、探索を一つのループで回す (ASPIRE)

CaP-X の評価段階 (S1〜S4、M1〜M4) は、この 2 軸に加えて、知覚 (シミュレータの真値か、ノイズのある知覚モジュールか) と、視覚フィードバック (画像の差分を言語化して返す Visual Differencing Module、VDM) でも条件を分けている。サーベイ資料によれば、CaP-X では LLM がコードを書き直すときのフィードバックとして生画像を返すと、stdout とエラーだけを返す場合より成功率が下がり、VDM が最もよかった (原論文で未確認)。これは生成モデルがコードを書き直す場面の結果で、Jev に型付きの問いで判定させる場面とは条件が違う。

## 3. 構成

### 比べる実装

比べる実装は次の 3 系統で、どれも同じ primitive と同じ観測を使う。違いは、次の動作や条件の真偽を誰が決めるかだけである。

- **A. 素朴な CaP**: LLM がタスク指示と物体一覧からコードを一度だけ生成し、そのまま実行する。条件分岐が要る場合は、物体姿勢の真値を使った幾何判定をコード内に書く
- **B. CaP + Jev 述語**: A と同じくコードを生成するが、条件判定を Jev の画像判定に任せる。判定が偽なら、コードに書かれたリトライや分岐に進む
- **C. Jev による直接操作**: コードを生成せず、Jev が毎回の判断で次の動作を選ぶ。選択肢の粒度を 2 通り試す
  - **C1. primitive 選択**: `hover / descend / grasp / lift / place / release` などの有限個の動作から選ぶ
  - **C2. 移動方向の選択**: 手先の x, y, z をそれぞれ `+ / 0 / -`、グリッパを `open / close / stay` から選ぶ。組合せは 3×3×3×3 = 81 通りで、Choice の上限 255 に収まる。4 つの問いに分けて並列に聞く方法もある

C1 と C2 には、先に意図 (掴む、運ぶ、離す) を選ばせ、その意図を入力に加えて動作を選ばせる 2 段階版も用意する。

先行研究の分類に当てはめると、A、B、C は次のようになる。

| 実装 | 生成コードが担う層 | 改善の段階 | 近い先行研究 |
|---|---|---|---|
| A. 素朴な CaP | API の組合せ | 1. ゼロショット生成 | CaP、ProgPrompt |
| B. CaP + Jev 述語 | API の組合せ | 2. タスク内での修正 | Code-as-Monitor、ProgPrompt の `assert` |
| C. Jev による直接操作 | 該当なし | 該当なし | Gemini API の `move(x, y, high)` と `setGripperState(opened)` を 1 歩ずつ呼ぶ例 |

B と Code-as-Monitor の違いは、実行中の条件判定を誰が行うかにある。Code-as-Monitor は生成コードの中で空間と時間の制約を計算して失敗を検出する。B は、その判定を Jev の画像判定で行う。C はコードを生成しないので CaP の分類には入らず、関数呼び出しを 1 歩ずつ行う方式の一種にあたる。レポートでは C を CaP の比較対象として置く。

### Jev への入力

Jev が判断する B と C には、入力を次の 3 通り用意する。A は Jev を使わないので対象外とする。

- **JSON**: シミュレータから取った物体の名前と姿勢の真値、グリッパの状態、接触。物体の識別はシミュレータが済ませている
- **画像**: agentview (斜め上からの固定カメラ) の画像だけを渡す。Jev が画像中の物体を見分け、指示と対応づける必要がある
- **画像 + JSON**: 両方を渡す

| | JSON | 画像 | 画像 + JSON |
|---|---|---|---|
| B (述語) | 省く | ◯ | 余裕があれば |
| C1 (primitive 選択) | ◯ | ◯ | ◯ |
| C2 (方向選択) | ◯ | ◯ | ◯ |

C の JSON 入力は先行事例の 2 つの投稿と同じ条件で、これを基準に、物体の識別を Jev に任せたときに何が変わるかを測る。B の JSON 入力を省くのは、真値の座標があるなら幾何判定のほうが正確で、算術が苦手な Jev に座標を比べさせても得るものが少ないからである。

予想としては、粗い判断で済む C1 は画像だけでもある程度動き、C2 は画像 + JSON が最もよくなると考えている。斜め上からの 1 枚の画像では、奥行き方向の位置合わせが難しいからである。把持の位置合わせには、手首カメラ (`robot0_eye_in_hand`) の画像を足す手もある。Jev が 1 回の問いで複数の画像を受け取れるかは未確認。

シミュレータは Jev の応答を待ってから進められるので、レイテンシは成功率に影響しない。所要時間は別に記録する。

### B の生成コードと API

B では、指示ごとに LLM が 1 回だけ方策コードを書き、そのコードの実行中に Jev を何度も呼ぶ。

```
指示 ──▶ LLM が方策コードを生成 (指示ごとに 1 回)
           │
           ▼
   def policy():
       pick(cream_cheese); place(cream_cheese, bowl)
       if not check("the cream cheese is in the bowl"):  # 述語 (Noul)
           retry()
       pick(bowl); place(bowl, plate)
       if not check("the bowl is on the plate"):         # 終了判定と再試行
           retry()
           │
           ▼
   知覚 API (物体姿勢の真値) / 制御 primitive (OSC の経由点 + min-jerk)
           │
           ▼
   LIBERO (robosuite, MuJoCo, Franka Panda)
```

LLM に渡す API は 3 種類に分ける。

- 知覚 API: 物体名の一覧、物体の位置と姿勢、グリッパの状態。シミュレータの真値から返す。
- 制御 primitive: 後述の `move_to`、`pick`、`place` など。
- 述語 API: `check(question) -> bool`、`choose(question, options) -> option`。中身は、A では真値の幾何判定、B では Jev の画像判定に差し替える。

生成コードの出来の違いが結果に混ざらないように、比較実験ではタスクごとに生成したコードを固定し、述語の実装だけを入れ替える。コード生成の成功率は別に記録する。

### 物体位置の扱い

primitive の目標座標は、シミュレータの物体姿勢の真値から取る。CaP 原論文のシミュレーション評価 ("scripted object detector") と、CaP-X の Privileged 設定 (S1) と同じ扱いで、レポートにそう明記する。JEV-27B-VL の例で把持位置が 3 cm 以上ずれたように、画像から物体の位置を取る方法では把持に必要な精度が出ない可能性が高いので、位置は真値から取り、Jev には判定と選択だけを任せる。

この設定では、真値の幾何判定が判定器として最も正確になる。このため、B の比較では幾何判定を上限 (oracle) として扱う。知覚の誤差を入れたい場合は、真値にノイズを加える条件を足す (CaP-X の Noisy に相当)。

### 制御 primitive

LIBERO の既定のコントローラは OSC_POSE で、action は手先の位置と姿勢の差分にグリッパを加えた 7 次元、制御周期は 20 Hz である。OSC がヤコビアンと質量行列から関節トルクを計算するので、関節角度を指定する必要はない。

primitive は、PARC2026-pre (`~/ghq/github.com/pokutuna/PARC2026-pre`) の実験 031 で作った経由点追従 (min-jerk 補間と PI 制御) を移植し、`move_to(pose)`、`pick(obj)`、`place(obj, target)`、`open_gripper()`、`close_gripper()` などを用意する。実験 031 では、LIBERO のシーンでボウルを皿に置く操作が 20/20 成功している。C2 の 1 判断あたりの移動量 (例えば 1〜2 cm) は、この上に作る。

## 4. タスク

### シーン

物体が多く、agentview で全体が収まるシーンを選ぶ。摂動 (照明、カメラ、配置のずらし) は扱わないので、LIBERO-Plus は使わず、LIBERO 本体のシーンで新しいタスクを定義する。

第一候補は LIBERO-Goal のシーンである。固定物に木製キャビネット (引き出し 3 段)、コンロ、ワインラックがあり、可動物に黒いボウル、皿、クリームチーズ、ワインボトルがある。PARC2026-pre で扱ったシーンなので、把持の癖が分かっている。

第二候補は LIBERO-90 の LIVING_ROOM_SCENE2 で、可動物がアルファベットスープ、クリームチーズ、トマトソース、ケチャップ、オレンジジュース、牛乳、バター、かごの 8 個ある。PARC2026-pre の実験 028 では、xy 方向の半径が約 0.025〜0.030 m より小さい物体は把持の成功率が低かった (バターは 0%)。このシーンを使う場合は、掴む物体をこの条件で選ぶ。

Jev の画像入力は一辺 280 px 以上を求めるので、agentview を LIBERO の既定 (`camera_heights=128`) より高い解像度で描画する。

### タスク案

タスクは 3〜4 個に絞り、少なくとも 1 個は難しいもの、または 2 ステップ以上のものにする。LIBERO-Goal のシーンでの案は次のとおり。

| 種類 | 例 | 必要な判断 |
|---|---|---|
| 基本 | ボウルを皿に置く | なし (動作確認と基準) |
| 未知の組合せ、2 ステップ | クリームチーズをボウルに入れ、そのボウルを皿に置く | 1 段目の成功確認 |
| 逆操作 | コンロの上のボウルを元の位置に戻す、ラックのワインボトルを取り出してキャビネットの上に置く | 初期状態の把握 |
| 難しい | 引き出しを開け、ボウルを入れて閉める | 開いたかの判定、リトライ |

成功判定は、BDDL の述語 (On、In、Open、Close) に合わせて、シミュレータの真値から計算する。どの実装の評価にも同じ判定を使う。

PARC2026-pre の実験 028 では引き出しを開ける閉ループ制御が 0/6 だった。引き出しを開ける primitive が安定しなければ、「難しい」枠は別のタスクに替える。

## 5. 評価

全部の組合せ (A、B、C1 × 3 入力、C2 × 3 入力の 8 構成) を 4 タスクで 20 エピソードずつ回すと 640 エピソードになるので、2 段階に分ける。

1. 探索: C1 と C2 を 3 入力それぞれで 10 エピソードずつ回し、入力ごとの傾向を見る。2 段階版は、この結果を見て加えるか決める
2. 本番: A、B、C1 と C2 で最もよかった入力の 4 構成を、4 タスク × 20 エピソード (計 320) で比べる

測る量は次のとおり。

- タスクの成功率
- 述語の正答率 (B)。述語を呼ぶたびに、真値の幾何判定の値を正解として記録する
- 1 エピソードあたりの Jev と LLM の呼び出し回数、費用、所要時間
- 判定のぶれ。同じ入力を複数回送り、答えが反転する割合を測る
- 失敗の分類: 把持の失敗、判定の誤り、計画の誤り、到達不能

余裕があれば、評価と予測の問いの差も測る。同じ場面で、把持の前のフレームに「この把持は成功するか」と聞く場合と、把持の後のフレームに「物体を把持しているか」と聞く場合の正答率を比べる。C で Jev が選ぶ動作には、結果の予測を含むものがあるので、この差は C の失敗の説明に使える。

## 6. 発展 (任意)

学習で加点を狙う場合は、述語モデルの蒸留を行う。シミュレータは述語の正解ラベルを無料で出せるので、画像と問いと正解の組を集めて NanoJev (Qwen3-0.6B ベース、MIT ライセンス) を fine-tune し、B と同じ条件で比べる。

もう一つは、VLA を制御 primitive の一つとして使う形である。`vla("put the bowl on the plate")` で LIBERO 用の pi0.5 や SmolVLA を呼び、完了を Jev が判定する。Harness VLA が LIBERO-Pro で同じ方向の結果を出している。GPU が必要になる。

C で逆操作タスク (置いたものを元に戻す) が解けるなら、その軌跡を記録して PARC2026 の学習データに使える可能性もある。外部モデルで作ったデータを学習に使ってよいかは PARC の規約を確認していない。この部分は PARC の非公開情報に触れやすいので、最終課題の公開リポジトリには入れない。

### 初日に確認すること

1. LIBERO が Mac で動き、agentview の画像を 280 px 以上で取得できる。Mac でのオフスクリーン描画 (`MUJOCO_GL` の設定) で詰まる可能性がある
2. 環境のラッパを作る。`observe()` は画像と物体姿勢の真値とグリッパの状態を返し、`step(delta)` は OSC の 7 次元の差分を渡す。`move_to(pos)` は単純な P 制御でよく、`set_object_pose(name, pose)` で物体を指定の姿勢に直接置けるようにする
3. Jev 1.14 Preview に画像を渡して、Choice の問いに答えが返る
4. 画像入力が実用になるかを見る。`set_object_pose` で「ボウルが皿の上にある、ない、縁に乗っている」などの場面を真値付きで作り、Jev の判定と真値の一致率と応答時間を数十枚で測る。続いて、基本タスクで C1 を数エピソード試す

1 か 2 で詰まった場合は、robosuite 標準の環境で同じ構成にする。4 で画像入力が使い物にならなければ、C は JSON 入力を主にし、画像は B の述語だけに使う。

## 11. リスクと対処

成功率は制御 primitive の信頼性に大きく左右され、述語や入力の違いが見えにくくなるおそれがある。物体の位置は真値に固定し、述語の正答率をタスクの成功率とは別に測ることで、Jev の判定の効果を切り分ける。

Jev の画像入力は公式には実験機能で、品質と提供の継続は保証されていない。判定のぶれには、複数回の多数決か確信度の閾値で対処し、その効果も記録する。

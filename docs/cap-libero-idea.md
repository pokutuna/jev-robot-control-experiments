# 応用編1 最終課題 計画: 画像だけで Jev はロボットを動かせるか

応用編1 の最終課題 (締切 2026-11-02 10:00) の計画。課題の要件は [lecture99_final_SUMMARY.md](../lectures/advanced1/99/lecture99_final_SUMMARY.md) にある。Microduck を使う別案は [sock-retrieval-plan.md](sock-retrieval-plan.md) にある。

仮タイトルは「画像だけで Jev はロボットを動かせるか: System 1 モデルに何を補えばロボットを操作できるか」とする。最後の実験で Code as Policies (CaP) と組み合わせられれば、タイトルにも CaP を入れる。

## 1. 題材と問い

Franka Panda がシミュレータ (LIBERO) 上で卓上の物体を運ぶ。System 1 モデルの Jev に、カメラ画像とロボット自身の状態 (手先の位置、指の開き) を渡して、ロボットを動かせるかを試す。実行中の物体の位置の真値は方策に渡さず、画像から物体の位置を推定する処理も作らない。その代わり、既知のカメラの校正値と、人が決めたこのタスクの手順と掴み方を補う (「タスクに固有の知識」)。

Jev をロボットに使った公開デモはいくつもあるが、どれも物体の位置などの環境の情報をテキストで渡していて、画像は渡していない (2 節)。Jev は 1.14 から画像を受け付けるようになったので、画像だけで同じことができるかを確かめる。

答えたい問いは次の 2 つである。

1. Jev の画像への答えのうち、どの問い方の答えなら、ロボットの動きに使えるか
2. このタスクを終えるまでに、Jev の答えのほかに何を人 (または LLM) が補う必要があったか

一連の実験は、前の実験の失敗を見て仮説を立て、方策を変えて確かめた探索の記録である。1 つの実験で変えたことが 1 つとは限らず (005 は多くを同時に変えた)、要因を 1 つずつ確かめたものではない。結論は「試した構成ではできた、できなかった」の形で書く。

先行事例の形 (001) では、真値のほかに、意図を選ぶ条件の真偽、真値から計算した行き先、行き先までの距離で変える歩幅もコードが作っている。002 はこれらも外すので、001 と 002 の比較は、入力を画像に替えた効果だけを測るものではない。001 は、補助の強い参考の基準として置く。

各実験では、成功率に加えて、Jev が決めていることと、コードや人が書いたルールが決めていることを分けて書く。

## 2. 背景

### Jev

**Jev** は TypeSafe AI が 2026-09-15 に公開した System 1 モデルである。状態と型付きの問いを受け取り、型付きの答えと確率を返す。文章もコードも生成しない。問いの型は次の 4 つ。

- Choice: 最大 255 個の選択肢から選ぶ
- Score: 数値で採点する
- Noul: 真である確率を返す
- Box: 画像中の物体の矩形を返す (1.14 で実験的に追加)

レイテンシは 70〜500 ms、料金は入力 100 万トークンあたり $0.042 で出力は無料。算術や数え上げは苦手とされる。2026-09 の時点で文書は入力を「Text only」としていたが、2026-10 時点の `typesafe/jev-1.14` は、OpenRouter 経由で画像を data URL で渡すと受け付ける ([jev-openrouter.md](../wiki/findings/jev-openrouter.md))。このプロジェクトでは OpenRouter 経由で呼ぶ。

### Jev をロボットに使った調査の結果

第三者の調査レポート「System 1 モデルによるロボット制御」(https://claude.ai/artifact/U4YPf3bPJUhKo4FtsLR3Gm) は、Jev は入力に含まれる情報から選ぶ評価には強く、入力にない結果を見積もる予測には弱いとまとめている。根拠は次の結果である。

- 積み木の課題で、トルクを直接選ばせると 0/20 だった。スキルを選ばせると 9/20 で、手書きの制御器の 8/20 と同程度だった。初めて見る指示では 22/40 で、手書きの制御器の 3/40 を上回った。
- ALFWorld で、各選択肢の先読みの結果を入力に足すと、解けたゲームが 134 本中 42 本から 116 本に増えた。
- 同じ入力を繰り返し送ると、Choice の答えが 12% の割合で反転した。

### 公開デモは画像を渡していない

Jev をロボットに使った公開事例の一覧 ([awesome-jev.md](../wiki/sources/awesome-jev.md)) では、ロボットの事例はすべて、シミュレータやアプリが作った構造化した状態 (JSON、文章) を渡し、Jev が選んだ行動を別のコードが実行している。作者自身が次のように書いている。

- Dmytro Hrybov: 「Jev doesn't accept images, it gets simplified geometry and contacts as text here」
- Askable Arm: 「No images go to Jev」
- OpenRoboto: 状態の冒頭に `'source': 'MuJoCo geometry + contacts, not camera vision'`
- RomanSlack/jev-drone: 「Jev is not a vision model. It takes JSON and returns typed answers with probabilities.」

OpenRoboto は、軸ごとの「目標 − 手先」の差 (mm) を問いの文に書き、選択肢の説明に「差が正なら positive」と選び方まで書いている ([jev-robot-control-inputs.md](../wiki/research/jev-robot-control-inputs.md))。Jev は数値の符号を読めば答えられる。

| 先行事例 | Jev の役割 | 入力 |
|---|---|---|
| Dmytro Hrybov の投稿 (2026-09-18) | 1 回の更新を 2 回の呼び出しに分ける。何をするか (意図) を選び、次に腕と指の動かし方を選ぶ | 簡略化した幾何と接触のテキスト |
| openroboto-ai/jev-robot-control | 意図を選び、x、y、z を negative / hold / positive、指を開く / そのまま / 閉じるから選ぶ | シミュレータの真値と軸ごとの差 |
| Isaac Sin の投稿 (2026-09-18) | `hover / descend / grasp / lift / place` から選ぶ | 環境の状態の JSON |
| Dimweaker/jev-libero | LIBERO で、意図、接触と動きの種類、入力を順に選ぶ | シミュレータの真値 |
| AliUraish/Jev_SO101 | 画像は別の大きなモデル (Astra) が解釈し、Jev はスキルを選ぶ | 大きなモデルの解釈 |

### CaP の実装パターンの分類

CaP (Liang ら、arXiv 2209.07753) は、使える API と数個の例を LLM に与え、自然言語の指示から制御プログラムを生成させる手法である。講義では、基礎編第 1 回でロボットポリシーの 3 分類 (E2E、E2E 階層型、Code as Policies) の一つとして紹介され、例として CaP-X (Fu ら、arXiv 2603.22435) の CaP-Agent0 が挙がった。

CaP の後続研究は、第三者のサーベイ資料 (https://claude.ai/artifact/SqMM6HbtkAKE1cWcHHs1ww) にならい 2 つの軸で分類する。資料が引く論文の数値は原論文で確認していないので、レポートで使う前に確認する。同資料は、Jev を CaP と組み合わせた公開例はないとしている。

1 つ目の軸は、生成コードが制御のどの層を担うかである。

- **API の組合せ**: 人が作った primitive をコードから呼ぶ。LLM はタスクの手順と引数を決め、軌道や低レベル制御は API が担う。CaP、ProgPrompt (arXiv 2209.11302)、ChatGPT for Robotics (arXiv 2306.17582)、CaP-X
- **中間表現**: コードが価値マップ、コスト関数、制約、報酬を書き、軌道は最適化器やモーションプランナが解く。VoxPoser (arXiv 2307.05973)、ReKep (arXiv 2409.01652)、Language to Rewards (arXiv 2306.08647)、Code-as-Monitor (arXiv 2412.04455)
- **VLA との組合せ**: 手順の流れと解析的な primitive をコードが担い、把持など接触の多い部分を VLA に任せる。Harness VLA (arXiv 2607.08448) は LIBERO-Pro で VLA をリトライ可能な primitive として扱っている

2 つ目の軸は、生成コードをどう改善するかである。Jena ら (2026、arXiv 2608.01851) のサーベイは、実行結果のフィードバック、タスクをまたぐ記憶、複数候補の探索の有無で 5 段階に分けている。

1. ゼロショット生成: 一度書いて実行し、失敗はそのまま (CaP、ProgPrompt、VoxPoser)
2. タスク内での修正: 実行結果を見て書き直すが、修正はタスクが終わると捨てる (Inner Monologue、REFLECT、Code-as-Monitor)
3. スキルの蓄積: 検証したコードを保存し、別のタスクで再利用する (Voyager、DROC)
4. 進化的探索: 複数の候補を実行で評価し、よいものを変異させる (CaP-X、RoboEvolve)
5. 全部入りの閉ループ: フィードバック、記憶、探索を一つのループで回す (ASPIRE)

実験 005、006 の段階的なガイドは、人が書いた API の組合せの CaP に、Jev の画像判定を部品として埋め込んだものにあたる。実験 007 では、このガイドを LLM に書かせる (ゼロショット生成)。

## 3. 実験

### 共通の条件

- シミュレータ: LIBERO (robosuite 1.4.1、MuJoCo)、Franka Panda、OSC_POSE。sim、policy、evaluator を dora-rs のノードに分ける ([dora-nodes.md](../wiki/guides/dora-nodes.md))
- タスク: libero_90 の 60 番「pick up the black bowl on the left and put it in the tray」。黒いボウルが 2 つあり、左のボウルを木のトレイに入れる。余裕があれば 2 つ目のタスクを足す
- 方策への入力: 指示文、カメラ画像 (固定カメラ quarterview と手首カメラ、320 px)、ロボットの状態 (手先の位置と向き、指の開き)。物体の位置などの真値は渡さない。真値を渡すのは実験 001 だけ
- 命令: 手先の相対移動 (`move_delta`)、目標位置への移動 (`move_to`)、指の開閉。sim の制御器が命令を実行し、結果 (reached / timeout) を返す
- エピソード: init state 0〜9 の 10 回。時間が足りなければ 0〜4 の 5 回にする。判断の回数の上限は 120 回
- 成功: LIBERO の判定 (ボウルがトレイの中にあるか)
- Jev のモデル: `typesafe/jev-1.14`

### 001: 先行事例の問いの形を移す

OpenRoboto と Hrybov の問いの構造を LIBERO に移す。コードや問いの文をそのまま動かす再現ではなく、目標、条件、歩幅はこのタスクに合わせて書く。1 回目の呼び出しで意図 (近づく、下ろす、掴む、持ち上げる、運ぶ、下ろす、放す、終える) を選ばせる。2 回目で x、y、z を negative / hold / positive、指を開く / そのまま / 閉じるから選ばせる。問いの文には、真値から計算した軸ごとの「目標 − 手先」の差と、掴めているか、トレイの上にあるかなどの真偽を書く。

真値から作った目標と条件、手書きの制御則を渡したときにこのタスクが解けるかを確かめ、以降の実験の基準にする。

### 002: 画像だけで向きを選ぶ

001 の入力を画像に替え、x、y、z の向きと指、終わったかを 1 回の呼び出しで選ばせる。2026-10-26 に試した結果では、どの条件でも成功しなかった ([jev-c2-direction-policy.md](../wiki/findings/jev-c2-direction-policy.md))。固定カメラだけと手首カメラを足した場合、カメラの置き方 (agentview、quarterview)、画像に描いた軸の矢印、軸の定め方 (世界座標、画像に合わせた向き) を変えても、前後の向きはほぼ当て推量のままだった。

この実験では、代表の条件を共通の条件で回し直し、静止画で向きの正答率を測った結果と合わせて示す。

### 003: 画像に注釈を付ける

毎 step の物体の位置 (真値) は使わず、ロボット自身の状態と、事前に決めた校正値 (カメラの射影行列、印の基準の平面の高さ、手首の画像の × の位置) から計算できる印を画像に描く。

- 手首の画像を 180° 回し (指が上、画像の右が世界の +y)、手先の真下の点に赤い × を描く
- 固定カメラの画像に、手先の位置を射影した印を描く。カメラの内部と外部のパラメータと手先の位置から計算できる

問いは画像の中の向きにする。「× を目標に重ねるには、× を左右と上下のどちらへ動かすか」と問い、画像の向きから世界座標の向きへの変換はコードが固定の対応で行う。2026-10-26 の確認では、この形の問いへの答えは 72 組中 70 組で揃った。上下 (z) と指、終わったかも、この呼び出しで選ばせる。

### 004: 意図と動きを分ける

003 の問いの前に、意図を選ばせる呼び出しを足す。001 と同じ分け方で、入力だけが違う。

### 005: 手順のガイド

意図の並びと意図ごとの動き (縁へずらす量、当たるまで下ろす、閉じる前に上げる量、運ぶ高さ) をコードで決め、Jev には「目標が × のどちら側か」「トレイにボウルがあるか」と意図を問う。2026-10-26 の試行では、LIBERO の判定で 6 回中 5 回成功した ([jev-c2-staged-policy.md](../wiki/findings/jev-c2-staged-policy.md))。失敗と遅れは、手首カメラにトレイが写らないときに、トレイへの向きの答えが外れたことによる。005 では 003 の固定カメラの印も描き、トレイが手首の画像に写らないときは、固定カメラの画像の答えでトレイへ寄せる。

### 006: 運ぶ段の向きを固定カメラの画像で決める

005 では、運ぶ段の向きを決める画像を「トレイが手首の画像に写っているか」の答えで切り替えた。トレイから遠い所でこの答えが揺れ、手先が行き来した。006 では、運ぶ段の向きを固定カメラの画像の答えで決め、固定カメラの答えが左右も上下も none になったら手首の画像の答えで合わせる。

### 007: 手順を LLM に書かせる (CaP)

005、006 のガイドに相当するコードを LLM に書かせ、その中で Jev の画像判定を呼ぶ。LLM には、ロボットを動かす関数、Jev に画像を問う関数、このロボットと場面の事実、003〜006 で測った画像の答えの確かさを渡す。例のコードは渡さず、実行の結果を返して書き直させることもしない。

### 008: 静止画で問い方を比べる

エピソードの中では、向きの答えのよしあしを、下りる時機や手順の失敗と分けられない。手先を掴むボウルの近くの 21 か所に置いた静止画で、002、005、006、007 の問い方と、行き先の言い方の違いを比べる。真値は採点にだけ使う。

### 004-2: 静止画で掴む縁を行き先にする

ボウルは指の開きより大きく、縁を挟んで掴む。005 以降は中心に合わせてから縁へ +y に 6 cm ずらしている。008 と同じ静止画で、行き先を縁 (+y と −y、「edge」と「rim」) にして問い、縁を直接行き先にできるかを確かめる。実験の流れでは 005 の掴み方の根拠にあたるので、004 の次に置く。

### 009: 007 のコードで行き先の言い方だけを変える

007 の失敗は、ボウルの上に合わせる所のずれで決まった。007 のコードを変えずに、関数の中で Jev に渡す行き先の言い方を 006 と同じにして、ずれの原因が手順か言い方かを分ける。

### 010: 決まった距離ずらす代わりに縁へ寄せる

006、009 に残った失敗は、中心に合わせた所の +y のずれに、決まった距離 (+y に 6 cm) を足して掴んだことによる。006 の下ろす段の初めで、決まった距離ずらす代わりに、手首の画像で −y の側の縁へ寄せる左右の向きを問い、y だけを合わせてから下ろす (004-2 の結果から、x は中心に合わせたままにする)。

### 011: 010 までの知識を CaP のプロンプトに入れる

007 の LLM に渡したのは 006 までの知識だった。007 と同じ関数で、プロンプトの事実と測った傾向だけを替え、掴む縁の側 (−y)、行き先の言い方による答えの違い (008)、縁を行き先にしたときの答え (004-2) を書いて、コードを書かせ直す。手順は書かず、LLM が 010 と同じ形の手順を書くかと、そのときの成功を見る。

### タスクに固有の知識

どの実験も、毎 step の物体の位置は方策に渡さない (001 を除く)。ただし、次の値はこのタスクの場面に合わせて事前に決め、コードやプロンプトに書いている。レポートでは、これらを方策が自分で見つけたものとして扱わず、条件と限界として書く。

| 種類 | 値 | 使う実験 | 汎用性 |
|---|---|---|---|
| カメラの校正 | 固定カメラの射影行列 (sim の task の camera_matrix) | 003〜007 | 実機でもカメラの校正で得られる |
| 場面の幾何 | 黄色い点を描く基準の平面の高さ 0.44 m (`s1cap.marks.TABLE_Z`)。テーブルの面ではなく、このタスクでボウルとトレイの中心がある高さに合わせた | 003〜009 | 物の高さを知っていれば別の場面でも使える。高さの違う物には合わない |
| 場面の幾何 | 手首の画像の × の位置 (横 50%、縦 40%、`CROSS_UV`)。開始の高さで、掴む高さの点が写る位置として測った。開始の高さより下では手先の真下の点からずれる | 003〜009 | 開始の高さと掴む高さに依存する。位置合わせを開始の高さで行う理由でもある |
| 手順 | 寄る、下ろす、掴む、持ち上げる、運ぶ、下ろす、離す。下ろすときは当たるまで下げる。指の開きで持っているかを確かめる | 005〜007、009 | 物を運ぶタスクに共通する |
| 掴み方 | 縁はボウルの中心から +y に 6 cm、閉じる前に 1.5 cm 上げる、持っているとする指の開きは 3 mm | 005〜007、009 | このボウルとこの指に固有。別の物には決め直す |
| 掴み方 | 中心に合わせた後、−y の側の縁へ寄せる向きを問う (縁の側は人が決めた)。トレイに下ろす前のずらしは −y に 6 cm。閉じる前の上げ量と指の開きは 005 と同じ | 010、011 | 掴む点は Jev の答えで決まる。縁の側とトレイでのずらしは、このボウルと配置に合わせた。011 では縁の側をプロンプトに書き、手順は LLM が書いた |
| 問いの言葉 | 行き先の言い方 (「the center of the bowl to pick up」「the center of the tray」)、finish の条件 (トレイの中にボウルがある) | 005、006、009、011 | タスクの文から作れるが、このタスクに合わせて書いた。007 では LLM がタスクの文から書き、同じ画像でも向きの答えが大きく変わった (008、009)。011 では測った傾向としてプロンプトに書き、LLM は 10 本とも中心に「the center of the bowl to pick up」を使った |

005〜007、009 のガイドは、手順の流れは汎用的だが、掴み方の数値はこのボウルに固有である。汎用にするには、縁の位置や近づく側を画像の答えから決める必要がある。004-2 では、縁を行き先にすると y の向きは答えたが x の向きは答えなかった。中心で x と y を合わせた後に縁で y を合わせ直す形 (010) は 10/10 だった。この形は、掴む縁の側と測った傾向をプロンプトに書くと LLM も書いた (011)。掴む縁の側は人が決めており、画像から決めてはいない。

## 4. 評価

実験ごとに次を記録する。

- 成功率 (LIBERO の判定)
- 1 エピソードあたりの判断の回数、Jev の呼び出し回数、費用、レイテンシ、sim の step 数
- Jev が決めていることと、コードが決めていること
- 失敗の分類: 向きの誤り、把持の失敗、終わりの判定の誤り、判断の上限
- 向きの答えの正答率。判断ごとに、真値から計算した向きと Jev の答えを比べる。真値は評価にだけ使い、方策には渡さない

## 5. リポジトリの構成

- `src/s1cap/`: 方策、環境のラッパ、制御、記録など、実験に共通の実装。dora に依存させない
- `nodes/`: dora のノード (sim、policy、evaluator)
- `experiments/NNN-slug/`: 実験ごとのディレクトリ。課題、仮説、方法、結果、結論を書いた README、dataflow、実行の記録を置く。録画は代表的なものだけを置き、残りは git の管理から外す
- `docs/setup.md`: 環境構築と実行の手順。リポジトリ外のリソースは環境変数でパスを渡し、何をどこに置くかを書く
- `wiki/`: 作業で分かったこと

## 6. 講義との連続性

## 9. リスクと未決定事項

- 1 エピソードは sim の実時間 (20 Hz) で 1〜6 分かかる。10 エピソード × 6 実験で数時間になるので、条件を絞るか init state を 5 つに減らす
- Jev の画像入力は実験的な機能で、品質と提供の継続は保証されていない
- 同じ入力でも Jev の答えはぶれる。必要なら多数決か確率の閾値を使い、その効果も記録する
- タスクは libero_90 60 の 1 つだけで、別のタスクや別の物で同じ方法が働くかは確かめていない
- サーベイ資料が引く論文の数値は、原論文での確認が必要

PARC2026-pre の競技規約は CaP 型のタスクプランナーを禁止しているので、このプロジェクトの成果は PARC の提出物には使えない。最終課題のリポジトリは public にするので、PARC2026-pre から移植するのは自作のコードだけにし、競技の非公開情報 (リーダーボードの指示文、本選の評価タスク) は含めない。

# 004 段階を先に選ばせ、2 回の呼び出しで問う

## 目的

003 では、1 回の呼び出しで行き先、向き、高さ、指を同時に問い、ボウルの上に着く前に指を閉じた。004 では、先行事例 (001) と同じく呼び出しを 2 回に分け、1 回目で段階 (近づく、下りる、掴むなど) を選ばせ、2 回目にその段階を伝えて 003 と同じ問いをする。段階を先に決めれば、指を閉じる時機が合うかを確かめる。物体の位置の真値は渡さない。

## 条件

003 ([../003-marked-image/README.md](../003-marked-image/README.md)) と同じ画像、印、状態の文を使い、次の点だけを変えた。

| 項目 | 内容 |
| --- | --- |
| 呼び出し | 1 回の判断で 2 回。1 回目で段階、2 回目で向き、高さ、指、タスクを終えたか |
| 1 回目の問い | 「Looking at the images and the robot state, which phase should the robot do next?」。選択肢は approach、descend、grasp、lift、carry、lower、release、finish。各選択肢には段階の説明 (例: grasp は「close the fingers on the rim of the bowl」) だけを書き、選ぶ条件は書かない |
| 2 回目の問い | 状態の文の最後に「Current phase: 段階 (説明)」を足す。行き先を、approach と descend では「the bowl to pick up」、carry と lower では「the tray」とする |
| 横の動き | approach、descend、carry、lower のときだけ動かす。他の段階では横に動かさない |
| 終わり | 1 回目で finish を選ぶか、2 回目でタスクを終えた確率が 0.8 以上なら止める |

実装は `src/s1cap/jev_marked.py` (`JevMarkedPolicy`、`two_call=True`)、dataflow は [dataflow.yml](dataflow.yml)。

## Jev が決めていることと、コードが決めていること

| Jev | コード |
| --- | --- |
| 次の段階 (画像と状態から、条件の手がかり無しに選ぶ) | 段階ごとの行き先の名前 (ボウルかトレイか) |
| 行き先が手首の画像に写っているか | 写っている確率が 0.5 以上なら手首の画像の向き、そうでなければ固定カメラの画像の向きを使う |
| × と黄色い点を寄せる画像の中の向き | 画像の中の向きを世界座標の水平の向きに直す (003 と同じ)。横に動かす段階を決める |
| 高さ (下げる、保つ、上げる) | 1 歩の大きさ (各軸 2 cm)。下げる命令は 40 step で打ち切る |
| 指を開くか閉じるか | 指の答えの確率が 0.7 以上で、今の状態と違うときは、移動を送らず指の命令だけを送る |
| タスクを終えたか | 終えた確率が 0.8 以上で止める |

001 との違いは、段階の選択肢に「選ぶ条件」を書かず、条件の真偽もコードが作らないことである。段階は Jev が画像から判断する。

## 結果

[results.md](results.md) の表を要約する。

- 成功 0/10 (LIBERO の判定)。どのエピソードも判断の上限 (120 回) まで続いた
- ボウルを持ち上げたエピソードは無い。表の「ボウルの持ち上げ」の 0.9〜4.1 cm は、手先がボウルを押して傾けたときの高さである (傾きは最大 20〜75°)
- 手先と掴む点の最短距離は 0.5〜5.5 cm
- 1 エピソード: 120 回の判断 (Jev の呼び出しは 238 回)、平均 6240 step (312 秒)
- 1 回の判断のレイテンシ (2 回の呼び出しの合計) は平均 872 ms。呼び出しごとには、段階が 435 ms、向きなどが 437 ms
- トークン: 1 エピソードで入力 36.7 万、出力 3.9 万

代表的な動画: [videos/init0.mp4](videos/init0.mp4) (左が固定カメラ、右が手首カメラ。Jev に渡したものと同じ印が描かれている)

### 段階の選び方

10 エピソードで選んだ段階の合計は、grasp 453、descend 412、approach 317、lift 7、carry 1 だった。lower、release、finish は一度も選ばなかった。

- 最初に指を閉じたのは 73〜153 step の grasp の段階で、手先はテーブルから 15〜22 cm の高さ、ボウルの中心から水平に 5〜13 cm 離れていた。どのエピソードも、ボウルの上に着く前に掴む段階に進んだ
- 段階は 1〜数回ごとに approach、descend、grasp の間を行き来した。init 3、4、5 は grasp と descend を交互に選び続け、grasp が 90〜108 回になった
- 2 回目の問いの答えは、段階とずれていた。approach を選んだ 317 回のうち 260 回で高さを down と答え、横に寄りながら下りた。descend を選んだ 412 回のうち 137 回で指を closed と答えた

### 失敗の仕方

1. 手先が高い所にあるうちに grasp を選び、指を閉じた (init 2 は最後まで指を閉じなかった)
2. 閉じた指のまま下り、ボウルの縁に当たって押した。テーブルの高さに着いたのは 359〜560 step で、003 (207〜349 step) より遅い。approach や grasp で横や指だけを動かす判断が増えたためと考えられる
3. 以後はテーブルに手先を押し付けたまま動き、命令の 69〜88% が timeout で終わった

### 横の向き

003 と同じく、送った移動の向きが掴むボウルの中心へ近づく向きだったかを、向きを決めた画像ごとに数えた (10 エピソードの合計)。ボウルの中心から 2 cm 以上ずれている軸だけを数えた。「なし」は横に動かさない段階 (grasp、lift) の判断である。

| 向きを決めた画像 | 軸 | 判断 | 近づく | 動かさない | 遠ざかる |
|---|---|---|---|---|---|
| 手首カメラ | x (前後) | 127 | 35 (28%) | 43 (34%) | 49 (39%) |
| 手首カメラ | y (左右) | 122 | 108 (89%) | 11 (9%) | 3 (2%) |
| 固定カメラ | x (前後) | 499 | 277 (56%) | 200 (40%) | 22 (4%) |
| 固定カメラ | y (左右) | 423 | 148 (35%) | 125 (30%) | 150 (35%) |
| なし | x (前後) | 395 | 0 | 395 (100%) | 0 |
| なし | y (左右) | 342 | 0 | 342 (100%) | 0 |

- 手首の画像の左右 (y) は 9 割が近づく向きだった。前後 (x) は 003 (遠ざかる 1%) と違い、4 割が遠ざかる向きだった。原因は確かめていない
- 固定カメラの画像の左右は、003 と同じく当て推量に近かった

## 003 との違い

| | 003 (1 回の呼び出し) | 004 (2 回の呼び出し) |
| --- | --- | --- |
| 成功 | 0/10 | 0/10 |
| 最初に指を閉じた高さ | テーブルから 7〜25 cm | 15〜22 cm |
| テーブルの高さに着いた step | 207〜349 | 359〜560 |
| 判断ごとのレイテンシ | 442 ms | 872 ms |
| 1 エピソードの入力トークン | 21.4 万 | 36.7 万 |

段階を先に選ばせても、指を閉じる時機は早いままだった。呼び出しが 2 回になり、時間とトークンはおよそ 2 倍になった。

## 分かったこと

- 段階の選択肢に「選ぶ条件」を書かず、画像から段階を選ばせると、Jev は手先がボウルの上に着く前に grasp を選ぶ。段階を 1 つの呼び出しに切り出しても、指を閉じる時機の判断は改善しなかった
- 001 では、段階の説明文に「grasp_pose_reached が真なら」のような条件を書き、その真偽を真値からコードが計算していた。004 の結果から、001 の成功は、段階を選ぶ判断そのものよりも、この条件の真偽に支えられていたと考えられる
- 005 では、段階を選ぶ条件をコードがロボットの状態と画像への答えから作り、段階ごとの動きもコードで決める

# 013 真値を文で渡す方策を、プリンの箱をトレイへ運ぶタスクで回す

## 課題

予備実験 001 では、物体の位置の真値を文で渡し、Jev に意図と軸ごとの向きを選ばせる方策が、libero_90 60 (左の黒いボウルをトレイへ) を 10/10 で終えた。レポートの本筋のタスクは libero_90 61 (プリンの箱をトレイへ) で、運ぶ物の形と掴み方 (ボウルは縁、箱は中心) が違う。同じ方策がこのタスクでも働くかは確かめていなかった。この結果を、真値を渡さない以後の実験 (014、017、CaP) と比べる基準にする。

## 仮説

運ぶ物と掴む点を替えれば、001 と同じ問いの形で、Jev は task 61 も 10/10 で終える。Jev がしているのは文に書かれた差の符号と真偽を読むことなので、運ぶ物の形は結果に影響しない。

## 方法

方策は 001 と同じ `s1cap.jev_text.JevTextPolicy` で、問いの形も 001 と同じである ([001 の README](../001-text-baseline/README.md) の「方法」)。001 から替えたのは次の点だけである。

| 項目 | 001 | 013 |
| --- | --- | --- |
| タスク | libero_90 60 (左の黒いボウル) | libero_90 61「pick up the chocolate pudding and put it in the tray」 |
| 運ぶ物の呼び方 (state のキーと問いの文) | bowl | pudding box |
| 掴む点 | ボウルの中心から +y に 6 cm、上に 3 cm (縁) | 箱の中心 (箱の y の幅は 4.6 cm で、指の開き 8 cm より小さい) |
| 離す点 | トレイの位置から +y に 6 cm、上に 6 cm | トレイの位置から上に 5 cm |
| 画像の大きさ | 320 px (方策には渡さない。記録だけ) | 448 px (012) |

運ぶ物、掴む点、離す点は `s1cap.tasks` の `TaskSpec` でタスクごとに決める。init state は 0〜9。実行の記録には、動画を後から描き直すための MuJoCo の状態 (`sim_states.npz`) も残した。

```sh
uv run --env-file .env scripts/run_experiment.py run experiments/013-text-baseline --inits 0-9
```

## 結果

[results.md](results.md) の表を要約する。

- 成功 10/10 (LIBERO の判定)。どのエピソードも、掴む点に 0.3〜0.6 cm まで近づき、箱を 15 cm 持ち上げ、トレイの位置から 0.1〜0.5 cm の所に置いた
- 1 エピソード: 平均 83.1 回の判断 (69〜104)、Jev の呼び出し 164.2 回、1708 step (85 秒)。初めて成功と判定されたのは平均 1497 step
- 1 回の判断のレイテンシ (2 回の呼び出しの合計) は、エピソードごとの平均で 684〜826 ms、全体の平均で 727 ms
- トークン: 1 エピソードで入力 30.2 万、出力 1.8 万
- 意図の内訳 (10 エピソードの合計): approach 357、carry 237、lift 76、lower 61、withdraw 60、grasp 10、release 10、finish 10、最初の姿勢合わせ (setup) 10。掴み直しは無かった

`uv run scripts/direction_accuracy.py experiments/013-text-baseline` で、行き先 (持ち上げる前は掴む点、持ち上げた後は離す点) から 2 cm 以上ずれている軸について、送った移動の向きを数えた (10 エピソードの合計)。

| 段 | 軸 | 判断 | 近づく | 動かさない | 遠ざかる |
|---|---|---|---|---|---|
| 持ち上げる前 | x | 73 | 73 (100%) | 0 | 0 |
| 持ち上げる前 | y | 110 | 93 (85%) | 17 (15%) | 0 |
| 持ち上げた後 | x | 96 | 40 (42%) | 56 (58%) | 0 |
| 持ち上げた後 | y | 280 | 224 (80%) | 56 (20%) | 0 |

001 と同じく、遠ざかる向きは一度も選ばなかった。持ち上げた後の「動かさない」は、運ぶ高さまでまっすぐ上げる判断 (lift) である。

代表的な動画: [videos/init0.mp4](videos/init0.mp4) (左が固定カメラ、右が手首カメラ)。最後のフレームで、箱はトレイの中にある。

### 表から外した記録

init 3 の 1 回目 ([excluded-runs/init3-20261031-165527/](excluded-runs/init3-20261031-165527/)) は、8 回目の判断で送った移動の結果が policy ノードに届かず、方策が結果を待ったまま `MAX_STEPS` まで進んで止まった。sim には届いた命令で、同じ命令を同じ step に送り直すと、dora を通さない `RobotDriver` では step 172 に終わった。方策の判断の失敗ではないので、同じ init state で回し直したものを表に使った。そのときの dora のログの抜粋は [dora-errors.log](excluded-runs/init3-20261031-165527/dora-errors.log)、考えられる原因は [wiki/findings/dora-dataflow.md](../../wiki/findings/dora-dataflow.md) の「命令の結果が届かなかった例」に書いた。

## 結論

真値から作った目標と条件の真偽を文で渡す方策は、運ぶ物と掴む点を替えるだけで task 61 も 10/10 で終えた。軸の向きの選び方も 001 とほぼ同じ割合だった。運ぶ物の形が変わっても結果が変わらないのは、何をどこへ動かすかをコードが真値から計算して文に書き、Jev はその差の符号と真偽を読んでいるからである。この方策で Jev は知覚を担っていない。

001 より判断の数が多い (平均 65.3 回に対して 83.1 回) のは、主に approach が多いためである。

# Code as Policies の系譜

claude.ai の Artifact として公開された日本語の調査文書。副題は「Code as Policies: LLM が書くコードでロボットを動かす手法と実装パターン」で、分類は「ロボティクス / LLM によるロボット制御」。日付は「2026-10-26 調査」「2026-10-26 作成」。出所は「各論文の arXiv 版、公開コード、公式ブログ」と書かれ、末尾に生成元として docgen@pokutuna-plugins (https://github.com/pokutuna/claude-plugins/tree/main/docgen) が記されている。著者名は書かれていない。

## 要点

- Code as Policies (CaP) は、LLM にロボットの方策 (policy) を Python コードとして書かせ、`exec` で実行する手法。知覚 API と制御 API の使い方をプロンプトで見せる。Liang ら (Google, 2022, https://arxiv.org/abs/2209.07753) が提案した。
- タスク固有の学習データなしで新しい指示に対応でき、for や if による手順の組み立てと NumPy による座標計算を正確に行える点が、スキル名を並べる方式や画像から直接行動を出すモデルとの違い。
- 元論文の時点から指摘されていた弱点は、用意した API でできることしかできない、接触の多い連続的な動作が苦手、実行前に成功するかを判断できない、の 3 つ。
- 後続研究を次の 2 軸で整理する。
  - 軸 1 (生成コードが入る層): API 合成型、中間表現型、VLA 併用型
  - 軸 2 (生成コードを改善する仕組み): ゼロショット生成、閉ループ修復、スキル蓄積、探索、コード生成モデル自体の強化学習
- 2026 年の CaP-X は、LLM に渡す API の抽象度を下げるほど成功率が下がることを 12 のモデルで示した。CaP 系の性能は LLM の能力だけでなく、人間が用意する primitive の設計に大きく左右される。

## ロボットの出力をコードにする理由

表 1 は言語指示からロボットを動かす方式を、出力の種類で 3 つに分けて比べている。

- スキル名の列 (自然言語): 例は SayCan (2022) や CaP 論文の NL Planner ベースライン。表現できるのは用意したスキルの実行順序。スキルの集合が必要で、数値の空間推論は表現しにくい。
- 行動そのもの: 例は CLIPort、OpenVLA、π0 などの VLA。関節や手先の連続的な指令を表現する。大量のデモンストレーションによる学習が必要。
- プログラム: 例は Code as Policies とその後継。分岐、繰り返し、座標計算、知覚結果に応じた引数の決定を表現できる。知覚と制御の API が必要で、LLM はその組み合わせ方を書く。

コードの利点は、LLM がコード補完の学習で得た能力をそのまま使える点とされる。例として「ブロックを右側に縦一列に並べて」は、ブロックを数え、等間隔の点を計算し、各ブロックを置くループとして書ける。スキル名の方式では等間隔の点を表現できず、VLA では対応するデモが学習データにない限り難しい、と述べている。

## 元論文 Code as Policies の仕組み

### 構成

LLM が生成して実行されるプログラムを LMP (Language Model Program) と呼ぶ。システムは、ユーザーの指示を受ける最上位の LMP (`tabletop_ui`)、その中から呼ばれる下位の LMP (`parse_position` など)、未定義の関数を書く関数生成 LMP から成る。

図 1 (論文と公開コード google-research/code_as_policies をもとに作成) の流れ: ユーザーの指示 (例「右側にブロックを一列に並べて」) を最上位 LMP が受けて Python コードを生成し、`exec` で実行する。コードは知覚 API (`get_obj_pos` など、物体検出器 MDETR 等の出力)、下位 LMP (別のプロンプトで LLM を呼び値を返す)、関数生成 LMP (作った関数はスコープに追加され再利用される)、制御 API (`put_first_on_second` など) を呼び、制御 API がロボット (UR5e など) を動かす。

- 知覚 API: 物体検出器 (卓上では MDETR、移動マニピュレータでは ViLD) の出力を `get_obj_names()`、`get_obj_pos(name)`、`get_bbox(name)` などとして公開する。
- 制御 API: 卓上では `put_first_on_second(obj, target)` のような pick-and-place、ホワイトボードでは `draw(pts_2d)`、移動マニピュレータでは `goto_pos` や `pick_obj`。ユーザーへの応答用に `say(message)` もある。
- LLM は関数の中身には関与せず、呼び出し方と引数だけを書く。

### プロンプト

LMP のプロンプトは、使える関数を示す import 文と、「コメントで書いた指示」と「対応するコード」の組の例でできている。実行時には、その場面の物体一覧 `objects = [...]` の行と新しい指示のコメントを末尾に足し、続きを LLM に補完させる。公開コードの卓上タスク用プロンプトからの抜粋として、次の例が載っている。

```python
objects = ['cyan block', 'white block', 'cyan bowl', 'blue block', 'blue bowl', 'white bowl']
# make a line of blocks on the right side.
say('No problem! Making a line of blocks on the right side')
block_names = parse_obj_name('the blocks', f'objects = {get_obj_names()}')
line_pts = parse_position(f'a 30cm vertical line on the right with {len(block_names)} points')
for block_name, pt in zip(block_names, line_pts):
  put_first_on_second(block_name, pt)
objects = ['yellow block', 'red block', 'yellow bowl', 'gray block', 'gray bowl', 'red bowl']
# can you cut the bowls in half.
say('no, I can only move objects around')
```

最後の例は API でできないことを頼まれたときに断る応答で、CaP は「できないこと」の判断も例から学ばせる。

### LMP が LMP を呼ぶ

`parse_position('top right corner')` は通常の関数ではなく、別のプロンプトを持つ下位 LMP である。呼ばれると「位置を表す言葉を座標に変換するコード」を LLM に書かせて実行し、変数 `ret_val` の値を返す。そのプロンプトは、言葉による位置指定を Shapely と NumPy の計算 (`denormalize_xy`、`make_line`、`interpolate_pts_on_line`、`get_closest_point` など) に落とす例でできている。役割ごとにプロンプトを分けることで、最上位の LMP は「何をどの順に動かすか」に集中し、「右上の角」や「太陽色のブロック」の解釈は下位 LMP が担う。論文の卓上タスクでは `tabletop_ui`、`parse_obj_name`、`parse_position`、`parse_question`、関数生成用の LMP を組み合わせている。

### 階層的コード生成

公開コードは `stack_objects_in_order`、`make_line`、`get_closest_point` などを API として実装しておらず、LLM のコード中の未定義の関数は関数生成 LMP が書く。論文はこれを階層的コード生成 (hierarchical code generation) と呼ぶ。手順は次のとおり。

1. 生成コードを AST として解析し、呼ばれているのにスコープにない関数名を集める
2. 関数ごとに `# define function: pt = get_pt_to_the_left(pt, dist).` の形で使われ方を示し、関数生成 LMP に本体を書かせる
3. 書かれた本体にも未定義の関数があれば、深さ優先で再帰的に同じ処理を行う
4. できた関数をスコープに加えてから元のコードを実行する。生成した関数は以後の指示でも再利用される

文書は `stack_objects_in_order` の生成例 (`put_first_on_second` をループで呼ぶ関数) を載せているが、「仕組みを示すために作成した例で、論文の出力ではない」と断っている。

階層的に生成すると、1 回で長いコードを書かせるより正答率が上がった。論文のロボット向け関数生成ベンチマーク RoboCodeGen (37 問) では Codex davinci で 81% から 95% に、HumanEval では pass@1 が 34.9% から 39.8% に上がった。

生成コードは、import 文、`__` を含む識別子、`exec` と `eval` の使用を事前に検査してから、API だけを入れたスコープで `exec` される。文書はこれを最低限の安全策で、物理的に危険な動作を防ぐ仕組みではないとしている。

### 評価結果

表 2 (CaP 論文の表からの抜粋) は、シミュレーションの卓上タスクで、3 万件のデモで模倣学習した CLIPort、自然言語プランナー (NL Planner)、CaP の成功率 (%) を比べている。

| 条件 | タスク群 | CLIPort | NL Planner | CaP |
| --- | --- | --- | --- | --- |
| 既知の属性・既知の指示 | 長い手順 | 78.80 | 86.40 | 97.20 |
| 既知の属性・既知の指示 | 空間・幾何 | 97.33 | 対応不可 | 89.30 |
| 未知の属性・既知の指示 | 長い手順 | 36.80 | 88.00 | 97.60 |
| 未知の属性・既知の指示 | 空間・幾何 | 0.00 | 対応不可 | 73.33 |
| 未知の属性・未知の指示 | 長い手順 | 0.00 | 64.00 | 80.00 |
| 未知の属性・未知の指示 | 空間・幾何 | 0.01 | 対応不可 | 62.00 |

学習時に見た属性と指示では CLIPort と同程度だが、未知の属性や指示に対しては CaP の成功率の落ち方が小さい、と述べている。実機では UR5e による卓上の pick-and-place とホワイトボードへの描画、Everyday Robots の移動マニピュレータによるオフィスキッチンでの移動と pick-and-place を示している。

### 論文が挙げた限界

論文は CaP を「言語を解釈し、知覚の出力を処理し、制御の低次元なパラメータを決める」層に限定した手法と位置付けており、次の限界がある。

- 知覚 API が記述できる範囲を超えられない (例: 軌道が「がたついているか」を判定する API はない)。プロンプトを肥大化させずに公開できる制御パラメータの数は限られる
- 例より大幅に長い指示や、抽象度の異なる指示 (ブロックで 3 次元の構造物を作るなど) に弱い
- すべての指示が実行可能だと仮定しており、生成したコードが正しく動くかを事前に判断できない
- 異なる身体 (embodiment) をまたぐ計画は不安定

## 軸 1: 生成コードが入る層

制御をタスク計画、スキルの呼び出しと引数、目的関数・制約・報酬、軌道の生成 (動作計画・最適化)、低レベル制御 (関節の指令) の層に分け、LLM のコードをどの層に置くかで 3 つに分ける。図 2 (各論文の記述をもとにした概念図) によると、各型で各層を担うものは次のとおり。

- API 合成型: タスク計画とスキルの呼び出しを LLM のコードが担い、軌道生成と低レベル制御は API の内部 (人手の実装) が担う
- 中間表現型: タスク計画は LLM (段階の分割) または手法による。目的関数・制約・報酬を LLM のコードが担い、軌道は最適化器・MPC、低レベルはコントローラが担う
- VLA 併用型: タスク計画とスキルの呼び出しを LLM のコードが担い、目的関数の層は明示しない。軌道は非接触の局面を動作計画が、接触局面を VLA が担う

### API 合成型

人間が用意した primitive を LLM が組み合わせるプログラムを書く方式。

- ProgPrompt (Singh ら, 2022, ICRA 2023): 計画をタスク名を関数名にした Python 関数として書かせる。プロンプトには行動の import 文、環境内の物体一覧、例のプログラムを並べ、最後に未完成の関数定義を置く。例では行動の前提条件を `assert` で確認し、満たされなければ回復用の行動を行う書き方を示す。
- ChatGPT for Robotics (Microsoft, 2023): 高レベル関数のライブラリとプロンプト設計の原則を整理し、ユーザーとの対話でコードを修正しながらドローンやマニピュレータを動かした。
- CaP-X (Fu ら, ICML 2026): API の抽象度で系統的に評価した。`stack_objs_in_order()` のような人手のマクロを与える条件から、`solve_ik()` や `sam3_text_prompt()` のような下位ライブラリの関数だけを与える条件まで 4 段階を用意し、12 のモデルを比べた。成功率は抽象度が下がるにつれて単調に下がった。人間の専門家が書いたコードの平均成功率 88.5% に、単発の生成で並ぶモデルはなかった。
- 関数呼び出し (function calling) で primitive を 1 回ずつ呼ばせる方式も変種とされる。Gemini API のロボティクス向けオーケストレーションの例 (https://ai.google.dev/gemini-api/docs/robotics-orchestration?hl=en) では、`move(x, y, high)` と `setGripperState(opened)` をツールとして定義し、Gemini Robotics-ER が返す呼び出しをアプリ側で実行して結果を返すループを回す。ループや計算を 1 つのコードにまとめられない代わりに、1 手ごとに結果を見て次の手を決められる。

利点は、学習なしで新しい指示や物体に対応できること、座標計算や条件分岐を正確に書けること、生成物を人間が読み・検査し・修正できること。欠点は、API にない能力は使えず性能が primitive の設計に強く依存すること。CaP-X は、挿入や注ぐ動作のように視覚フィードバックを密に使う接触の多い動作でプログラムによる制御が脆いと述べている。

### 中間表現型

LLM に価値マップ、コスト関数、制約、報酬などを計算するコードを書かせ、最適化器や動作計画器に渡して軌道を作らせる方式。

- VoxPoser (Huang ら, 2023): LLM が VLM を呼び出すコードを書き、近づくべき場所 (affordance) と避けるべき場所 (制約) を 3 次元ボクセル上の値として合成する。動作計画器がこの価値マップから 6 自由度の手先の経由点を作り、外乱があれば計画し直す。
- ReKep (Huang ら, 2024): 画像上の 3 次元キーポイントを入力として数値のコストを返す Python 関数を、VLM に段階ごとに書かせる。段階の終わりに満たすべき条件 (sub-goal constraint) と途中で保つべき条件 (path constraint) を分け、階層的な最適化で手先の姿勢列を求める。知覚と行動のループを実時間で回せる。
- Language to Rewards (Yu ら, 2023): LLM が報酬のパラメータを書き、MuJoCo MPC が実時間で最適化する。四足歩行ロボットと多指ハンドの 17 タスクで約 90% を達成し、primitive を CaP で組み合わせるベースラインは約 50% だった。
- Code-as-Monitor (Zhou ら, 2024): 失敗の検出に使う。VLM が時空間的な制約を評価するコードを書き、実行中に違反を監視する。開ループの方策と組み合わせて閉ループにできる。
- Eureka (Ma ら, 2023, ICLR 2024) も報酬のコードを書かせるが、その報酬で強化学習を行い、最終的に動くのは学習した重み。サーベイ (Jena ら, 2026) はコードが実行時の方策になる系統とは分けて扱っている。

利点は、滑らかな連続軌道を作れること、物体が動いても LLM を呼び直さずに最適化器が同じコスト関数で解き直せること、primitive を網羅しなくてよいこと。欠点は、最適化器、動作計画器、場合によっては力学モデルを用意する必要があること、LLM が書いたコストが意図どおりの動きを表しているか実行するまで分かりにくいこと。

### VLA 併用型

LLM のコードが全体の手順と解析的な primitive の呼び出しを担い、つかむ・差し込むなど接触の多い局面だけを学習済みの VLA に任せる方式。

- Harness VLA (Zhang ら, 2026): 凍結した (追加学習しない) VLA を、失敗したらやり直せる接触用の primitive として扱う。位置特定 (grounding)、把持前の姿勢への移動 (staging)、搬送、移動、解放は少数の解析的な primitive が担い、エージェントはそれらと VLA の使い方を実行履歴、成功の規則、失敗のモデルとして記憶する。LIBERO-Pro で最も強い比較手法を 38.6 ポイント、RoboCasa365 で 25.4 ポイント上回ったと報告している。
- Gemini Robotics 1.5 (Google DeepMind, 2025): 上位の推論モデルと下位の VLA を組み合わせるが、受け渡しはコードではない。Gemini Robotics-ER 1.5 が計画を立て、各ステップの自然言語の指示を VLA の Gemini Robotics 1.5 に渡す。ER は Google 検索やユーザー定義の関数も呼べる。

利点は、接触の多い動作を primitive として手で実装しなくてよいこと、手順はコードとして読め VLA の失敗をコード側の再試行や再配置で補えること。欠点は、VLA の失敗のしかたを引き継ぐこと、VLA の推論環境と LLM の両方を動かすため構成と遅延の管理が増えること、VLA に渡す指示の粒度を設計する必要があること。

### 3 パターンの比較 (表 3)

| パターン | LLM が書くもの | 動きを決めるもの | 得意 | 苦手 | 代表例 |
| --- | --- | --- | --- | --- | --- |
| API 合成型 | primitive を組み合わせるプログラム | 人手で実装した primitive | 手順、論理、座標計算、未知の指示の組み合わせ | 接触の多い連続動作、API にない能力 | CaP, ProgPrompt, ChatGPT for Robotics, CaP-X |
| 中間表現型 | 価値マップ、制約、報酬、監視条件の関数 | 動作計画器、最適化器、MPC | 連続軌道、外乱への追従 | 最適化器やモデルの準備、コストの妥当性確認 | VoxPoser, ReKep, Language to Rewards, Code-as-Monitor |
| VLA 併用型 | 手順と primitive 呼び出し | 解析的 primitive と VLA | 接触の多い局面を含む長い手順 | VLA 由来の失敗、2 系統の統合 | Harness VLA |

## 軸 2: 生成コードを改善する仕組み

2026 年のサーベイ Weights or Skills? (Jena ら) は CaP 系の手法を自己改善の度合いで 5 段階に並べた。段階が上がるごとに、実行結果のフィードバック (F)、タスクをまたぐ記憶 (M)、複数候補の探索 (S) が加わる。表 4 (Jena ら 2026 の分類をもとに作成) の内容は次のとおり。表の空欄は、サーベイがその段階の定義でその仕組みを条件にしていないことを表す。

| 段階 | F | M | S | 内容 | 代表例 |
| --- | --- | --- | --- | --- | --- |
| 1. ゼロショット生成 | なし | なし | なし | 一度書いて実行する。失敗したら失敗のまま | CaP, ProgPrompt, VoxPoser, ChatGPT for Robotics, Demo2Code, RoboCodeX |
| 2. 閉ループ修復 | あり | なし | なし | タスク内で実行結果を見て書き直す。修正はタスクが終わると捨てる | Inner Monologue, REFLECT, Code-as-Monitor |
| 3. スキル蓄積 | | あり | | 検証済みのコードを保存し、別のタスクで取り出して使う | Voyager, LRLL, DROC |
| 4. 進化的探索 | あり | | あり | 複数の候補を実行で評価し、良いものを改変する | CaP-X, RoboEvolve |
| 5. 全体の閉ループ | あり | あり | あり | フィードバック、記憶、探索を 1 つのループで回す | ASPIRE, ENPIRE, RoboClaw |

### 閉ループ修復

実行後の状態を LLM に返してコードを書き直させる。CaP-X は複数ターンの条件を比べ、標準出力とエラーだけを返す場合より、生の画像を返す場合の方が成功率が下がることを示した。最も良かったのは、観測を「最初の場面の説明と、各ターンでの変化」のテキストに変換して返す Visual Differencing Module (VDM) を使う条件だった。

### スキル蓄積

うまく動いたコードを関数として保存し、後のタスクで呼び出す。

- 元論文の CaP でも、関数生成 LMP が作った関数はセッション中スコープに残り再利用される。
- Voyager (Wang ら, 2023): Minecraft で、自動カリキュラム、実行可能なコードのスキルライブラリ、環境のフィードバック・実行エラー・自己検証による反復的な修正を組み合わせ、新しいワールドでもライブラリを再利用してタスクを解いた。
- CaP-X の CaP-Agent0 は、成功した実行から合成した 9 個のタスク非依存な関数をライブラリとして持つ。
- ASPIRE (Lu ら, 2026, NVIDIA ほか): スキルをコードそのものではなく「失敗の特徴、適用する条件、修正の方針、必要ならコードの概略」という指針の形で保存する。コーディネータが各指針を監査し、再利用できるものだけをライブラリに入れる。著者らは、古いスキルや誤解を招くスキルが溜まることを限界として挙げている。

### 探索と学習

- Eureka は報酬コードの候補を複数生成し、強化学習の結果を見て良い候補を改変する進化的探索を行った。
- CaP-Agent0 は 1 つのモデルに 9 回、または GPT-5.2、Claude Opus 4.5、Gemini-3-Pro に 3 回ずつ問い合わせ、中央のエージェントが候補をまとめる。
- ASPIRE は各ラウンドで上位の候補と失敗の記録を条件に K 個の候補プログラムを作り、実行で評価する。LIBERO-Pro でのアブレーションでは、実行の記録を返す仕組みで平均成功率が 14% から 62% に、進化的探索を加えて 72% に上がった。
- CaP-X の CaP-RL は、Qwen2.5-Coder-7B-Instruct を、シミュレーションでの成否を報酬とする GRPO で訓練した。キューブを持ち上げるタスクの成功率はシミュレーションで 25% から 80%、実機の Franka で 24% から 84% に上がった。訓練前のモデルはつかむ手順を飛ばして目標の位置へ向かうことが多く、論文はこれを step skipping と呼ぶ。LLM の重みを更新するので、サーベイの段階表の外にある。

## 同じタスクを 3 つのパターンで書く

「赤いキューブを緑のキューブの上に積む」を例に、軸 1 の 3 パターンで LLM が書くコードを比べている。(a) は論文に載っている生成例、(b) と (c) は文書の著者が作成した説明用の例。

(a) API 合成型 (CaP-X の生成例、CaP-RL で訓練した後のモデルの出力の抜粋): `get_object_pose("red cube", return_bbox_extent=True)` で姿勢と大きさを取り、置く位置を `green_cube_pos + np.array([0, 0, red_cube_extent[2] / 2 + green_cube_extent[2] / 2])` で計算し、`sample_grasp_pose("red cube")` で把持姿勢を得て `goto_pose(grasp_pos, grasp_quat, z_approach=0.1)`、`close_gripper()` と続く。LLM が決めるのは手順と置く位置の計算で、把持姿勢の候補は `sample_grasp_pose`、軌道は `goto_pose` の内部 (逆運動学と動作計画) が決める。

(b) 中間表現型 (ReKep の形式に合わせた例): キーポイント 3 を赤いキューブの上面、4 を赤いキューブの底面、7 を緑のキューブの上面と仮定し、`num_stages = 2` として、stage 1 の sub-goal 制約 (手先をキーポイント 3 に合わせる)、stage 2 の sub-goal 制約 (キーポイント 4 を 7 の 2cm 上に置く)、stage 2 の path 制約 (`get_grasping_cost_by_keypoint_idx(3)` で赤いキューブをつかんだままにする) を書き、`grasp_keypoints = [3, -1]`、`release_keypoints = [-1, 3]` を指定する。関数は `end_effector` と `keypoints` を受け取り、0 以下なら満たされているコストを返す。手先の動かし方は書かれず、コストを最小化する最適化で決まる。緑のキューブが動かされてもキーポイント 7 の座標が更新されるだけで、同じ関数のまま解き直せる。

(c) VLA 併用型 (Harness VLA の構成に合わせた例、関数名は架空): `locate` で位置を測り、`move_above` (動作計画) で非接触の移動を行い、`run_vla("grasp the red cube", max_steps=150)` でつかむ局面だけを VLA に任せる。`is_grasped` で成否を確認し、最大 3 回まで位置を測り直して再試行する。その後 `run_vla("place the red cube on the green cube", max_steps=150)` と `release()` を行う。(a) と比べると把持姿勢を VLA が画像を見ながら決め、(b) と比べると目標状態をコストではなく VLA への自然言語の指示として渡している。

## 選ぶときの判断材料と限界

- API の設計が性能を決める: CaP-X は、複数ターンの対話、構造化した実行フィードバック、VDM、スキルの自動合成、複数モデルの合議といった推論時の計算を増やす手法で、低レベルの primitive しかない条件でも差を縮められると報告している。文書は、タスクで繰り返し使う操作 (把持姿勢の計算、積み上げ位置の計算など) を primitive として用意できるかが最初の判断材料になるとしている。
- 接触の多い動作: 挿入、注ぐ、柔らかい物体の操作のように視覚フィードバックを密に使う動作は API 合成型が最も苦手とする。外乱への追従が必要なら中間表現型、学習済みの VLA が使えるなら VLA 併用型が候補になる。
- 実行前に成否が分からない: 閉ループ修復や Code-as-Monitor のような監視がこの問題への対処である。生成コードの実行時検査は CaP の exec 前の文字列検査程度にとどまるものが多く、可動範囲や力の上限などの物理的な安全策は API や下位のコントローラ側に置く必要がある。Gemini API の例でも、ループに最大ステップ数を設けている。
- 遅延と計算コスト: LLM は指示ごと (下位 LMP を含めれば 1 つの指示で複数回) 呼ばれるため、指令の周期で回る制御ループには入れられない。生成済みのコードと中間表現型の最適化は LLM なしで速く動く。探索型は計算量が大きく、ASPIRE の実機実験では 1 つのタスクの実験に合計で数百万から数千万トークンを使っている (缶を持ち上げるタスクで、シミュレーションで得たスキルを与えると 61.94M から 6.58M トークンに減った)。

### 重みとして持つか、コードとして持つか

サーベイ (Jena ら) は、ロボットの能力を VLA の重みとして持つ方向と、実行可能なスキルのコードとして持つ方向を対比している。両者は排他的ではなく、組み合わせる研究も 2026 年に出てきている、と文書は述べる。表 5 (Jena ら 2026 をもとに作成) の内容は次のとおり。

| 観点 | 重み (VLA) | スキル (コード) |
| --- | --- | --- |
| 能力の所在 | 学習済みの重み | 読めるプログラム |
| 改善の方法 | データとパラメータを増やして再学習 | フィードバック、記憶、探索で勾配更新なしに改善できる (上位の段階のみ) |
| 汎化のしかた | 学習データの間の補間 | プログラムの組み合わせと探索 |
| 編集と監査 | 学習後に編集、監査、再結合できない | 検査、編集、再結合できる |
| 主な弱点 | 中身が見えず、実行時に失敗を直す仕組みがない | ゼロショットでは回復手段がない。下位の段階は修正を捨てる。探索は計算コストがかかる |

CaP-X の LIBERO-Pro での比較では、指示を変える摂動に対しては CaP-Agent0 が OpenVLA、π0、π0.5 を上回ったが、物体の位置を変える摂動では 3 つのスイートのうち 2 つで π0.5 の方が高かった。

### Jev について

Typesafe AI の Jev (2026, https://www.mindstudio.ai/blog/jev-system-one-model-launch) は、テキストを生成せず、構造化した状況と選択肢を受け取って確信度付きの判断を 1 回の推論で返すモデルとして紹介されている。Jev はコードを生成しないので CaP の LMP (コードを書く役) は担えない。組み合わせるとすれば、生成コードの中から呼ぶ判断関数として、列挙した選択肢から次の行動や回復手段を選ぶ役が考えられ、これは CaP の `parse_obj_name` のような下位 LMP の位置に生成型の LLM の代わりに判断モデルを置く構成にあたる、と述べている。ただし文書はこの構成を「本稿の推測」とし、CaP と組み合わせた公開例は見つけられなかったと書いている。公開されているロボティクス関連の評価は、シミュレーション上のデモと、ロボット群の障害対応を振り分ける判断層としての試験 (https://github.com/robokrunch/jev-physical-ai) にとどまる、としている。

## 用語

文書末尾の用語集の定義。

- 方策 (policy): 観測からロボットの行動を決める規則。CaP ではこれをコードとして書く
- LMP: Language Model Program。LLM が生成し、実行されるプログラム。CaP 論文の用語
- primitive: コードから呼び出す基本操作の関数 (つかむ、置く、移動するなど)。中身は人手の実装や学習済みモデル
- 知覚 API / 制御 API: 物体の名前や位置を返す関数と、ロボットを動かす関数。LLM に見せるのは呼び出し方だけ
- few-shot プロンプト: 指示と対応するコードの例をいくつか並べ、新しい指示の続きを書かせるプロンプト
- VLA: Vision-Language-Action モデル。画像と言語から行動を直接出力する学習済みモデル (OpenVLA、π0 など)
- VLM: Vision-Language Model。画像を入力に取れる言語モデル
- MPC: モデル予測制御。力学モデルで先の状態を予測し、コストを最小化する行動を毎周期計算する
- affordance: 物体や場所がどの行動に使えるか。VoxPoser では「近づくべき場所」を表す値
- キーポイント: 物体上の特徴的な 3 次元の点。ReKep の制約関数の入力
- pass@1: 1 回の生成で正解する割合
- GRPO: 同じ入力に対する複数の出力の報酬を比べて方策を更新する強化学習の手法
- LIBERO-Pro: 物体の位置や指示を変える摂動を加えた操作タスクのベンチマーク

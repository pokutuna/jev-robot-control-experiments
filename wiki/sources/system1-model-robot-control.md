# System 1 モデルによるロボット制御

claude.ai の Artifact として公開された日本語の調査レポート。分類は「調査レポート / ロボティクス」で、「2026-10-25 時点」「2026-10-25 時点の公開情報に基づく調査」と書かれている。末尾に生成元として docgen@pokutuna-plugins (https://github.com/pokutuna/claude-plugins/tree/main/docgen) が記されている。著者名は書かれていない。

TypeSafe AI の Jev に代表される System 1 モデルを、ロボットのどの層で、どの部品と組み合わせて使えるかを、2026 年 9 月から 10 月に公開された研究、デモ、オープンモデルから整理している。

## 要点

- System 1 モデルは、文章を生成せず、事前に定義した選択肢や尺度に対する確率だけを返すモデル。Jev は 70〜500ms で応答し、出力トークンに課金しないため、ロボットの制御ループの中で毎ステップ呼び出す使い方が試されてきた。
- 結論: Jev は入力に含まれる情報から選択肢を見比べる「評価」には強く、入力にない結果を予測する「シミュレーション」が必要な判断には弱い。トルクや関節角を直接選ばせる構成は失敗し、コードやシミュレータが各選択肢の結果を先に計算して Jev はそれを評価するだけ、という分担にすると手書きのコントローラと同等以上に動く。
- 実績のある組み合わせは次の 2 つに絞られる。
  - スキル選択 × コードによる結果予測: IK と PD 制御で実装したスキルを選択肢として並べ、Jev に次のスキルを選ばせる。新しい指示に対して手書きコントローラを大きく上回った。
  - 画像の二値判定 × 古典的な制御則: カメラ画像について「目標はグリッパの左か右か」のような少数択の問いに答えさせ、その答えでアームを少しずつ動かす。ピックアンドプレースで 75% を達成した。
- Code as Policies のように LLM がロボットのコードを書く手法と組み合わせる場合は、生成コードの中の条件判定を Jev に任せる形が既存の事例と整合する。この形の定量評価はまだ見つかっていない、としている。

## System 1 モデルと Jev

Jev は TypeSafe AI が 2026 年 9 月 15 日に公開したモデルで、名前の「System 1」はカーネマンの二重過程理論の速い直感的思考に由来する。利用者は判断材料となる state (テキストか JSON) と問いの一覧を送り、問いごとに型付きの答えと確率を受け取る。問いの型は 3 種類で、2026 年 10 月 14 日の Jev 1.14 で 4 種類目が加わった。

| 型 | 返すもの | ロボットでの使い道の例 |
| --- | --- | --- |
| Choice | 最大 255 個の選択肢から 1 つと、全選択肢の確率分布 | 次に実行するスキル、移動方向 |
| Score | 定義した段階尺度での評点 | 把持の安定度、作業の進捗度 |
| Noul | 命題が真である確率 | 「把持できているか」「作業は完了したか」 |
| Box (1.14 で追加) | 画像中の物体 1 つのバウンディングボックス | 対象物の位置の推定 |

- ベンダー自身が公開している弱点は、数値の精度が必要なタスク、数を数えること、state に無関係な情報が混ざったときの精度低下。ロボットや物理的な安全性についてのガイダンスはドキュメントにない。
- 画像入力は 1.14 の公開時に、1.13 と 1.14 の両方で使えるようになった。リクエストごとに `TypeSafe-Danger-Zone-Images: true` ヘッダーが必要で、ベンダーは本番利用に向かない実験機能と位置づけている。対応するのは 1 辺 256〜1,568 ピクセルの PNG と JPEG の静止画で、動画は扱えない。
- Box は対象が画像に写っていなくても「見つからない」と答えず、必ず何らかの枠を返す。

## 評価とシミュレーションの境界

この分野でまとまった定量研究は、現時点では Yang らの「Code Owns the Simulation, Jev Owns the Evaluation」(arXiv 2610.01834, https://arxiv.org/pdf/2610.01834) だけだとしている。この論文は判断を 2 種類に分ける。

- 評価: 入力と選択肢に含まれる情報だけで正解を判断できる判断
- シミュレーション: 相手の行動、先に済ませるべきサブゴール、行動後の物理状態のように、入力にない予測を経なければ正解が決まらない判断

論文の結果:

- 評価では高い精度。直感的な誤答に誘導する認知反射テストで 99% 正解し、行列ゲームでも相手の行動を教えれば 98% で最適な手を選んだ。
- シミュレーションが必要な判断では、タスクの文面に出てくる語を含む選択肢に引き寄せられる。家事テキストゲーム ALFWorld で「きれいなナイフを引き出しに入れる」という課題を与えると、ナイフをシンクで洗わずに引き出しへ直行した。著者らはこの振る舞いを、世界モデルを持たない方策にたとえている。
- この失敗は知識の欠如によるものではない。別の呼び出しで「相手はどう動くか」を聞けば 90% 正しく答え、その答えを state に書き戻して改めて手を選ばせると 94% で正解した。失敗するのは、1 回の呼び出しで予測と評価の両方をさせたとき。
- 著者らは、コードが予測を担い、Jev は評価だけを担う分担を提案している。

DeepMind Control Suite の Stacker での成功数 (論文の Table 3 より):

| コントローラ | 生トルクを選ぶ (既定タスク) | スキルを選ぶ (既定タスク) | スキルを選ぶ (新しい指示 5 種) |
| --- | --- | --- | --- |
| Jev | 0/20 | 9/20 | 22/40 |
| 手書きコントローラ | 対象外 | 8/20 | 3/40 |
| ランダム | 0/20 | 1/20 | 0/40 |

生トルクの条件では、トルクの良し悪しはアームが次にどう動くかで決まり、その予測は入力に含まれない。スキルの条件では、各スキルは IK と PD 制御で実装されており、選択肢の説明を読めば実行後の結果が分かる。この差が成功数の差になったと論文は説明している。ただし両条件は行動の粒度も異なるため、差のすべてを予測の有無に帰せるわけではないと著者ら自身も断っている。

図 1 (コードが予測し Jev が評価する分担) の流れ: 現在の状態 → コードが候補を列挙し各候補の結果を予測 → Jev が結果付きの候補を評価して 1 つ選ぶ → コードが選ばれたスキルを IK と PD 制御で実行 → 環境が変化 → 現在の状態に戻る。予測を担うのはシミュレータ、ゲームのコピー、スキル実装のいずれでもよい。

同じ分担はテキストゲームでも効いた。ALFWorld で各コマンドをゲームのコピーで先に実行し、表示される結果と新たに可能になるコマンドを選択肢に添えると、解けたゲームは 134 中 42 から 116 に増えた。同じ先読み情報を使った単語一致ルールは 18 しか解けなかったため、改善は先読み情報そのものではなく Jev がそれを評価したことによる、としている。

## 適用場所による分類

公開事例を、Jev に決めさせている内容がロボットのどの層にあたるかで 6 層に分ける。層が下がるほど、正しい選択に必要な物理的な予測が増え、Jev の成績が落ちる。

| 層 | Jev が決めること | 結果 | 主な事例 |
| --- | --- | --- | --- |
| ① 低レベル制御 | トルク、関節角、モーターコマンド | 失敗 | Stacker の生トルク 0/20、JEV-27B-VL の 8 択モーターコマンド 0/10 |
| ② 動作プリミティブ | XYZ の移動方向、グリッパの開閉 | 動くが単発の記録が中心 | OpenRoboto の xArm7、Franka と Allegro ハンドのキューブ積み、jev-libero、Unitree G1 |
| ③ スキル選択 | 次に実行するスキル | 最も実績がある | Stacker のスキル選択、Askable Arm、JEV control your roboarm、MakerMods、MOSS |
| ④ 知覚判定 | 画像や状態についての少数択の問い | 制御則と組めば有効 | JEV-27B-VL の左右・上下判定 (75%) |
| ⑤ 監視とゲート | 完了したか、危険か、上位に回すか | 補助役として有効 | Jev_SO101、確信度ゲート、ドローンの引き継ぎ |
| ⑥ オフライン | ロボットデータの評価とラベル付け | 制御ではない応用 | ヒューマノイド遠隔操作データの区間分割 |

### ① 低レベル制御

Stacker で 0.02 秒ごとに 5 つのアクチュエータのトルクを 5 段階から選ばせた条件では、20 エピソードで一度も箱を掴めなかった。手が箱に最も近づいた距離の平均は 25cm で、ランダムなトルクの 16cm より遠かった。画像版のオープンモデル JEV-27B-VL でも、8 種類のモーターコマンドから直接選ばせると 10 シーン中 0 回の成功だった。

### ② 動作プリミティブ

移動方向とグリッパ操作を離散化して選ばせる構成は、シミュレーション上では課題を達成している。

- OpenRoboto の比較: MuJoCo の xArm7 でりんごを皿に置くタスクを、Jev 1.13 が 113 サイクル、約 0.019 ドルで達成し、GPT-6 Astra は 106 サイクル、約 5.93 ドルだった。
- Franka と Allegro ハンドのキューブ積み: Jev が 19.1 秒・0.0006 ドル、Claude Opus 5 が 158.8 秒・0.75 ドル。
- どちらも各コントローラ 1 回の記録で、成功率の推定ではない。
- Unitree G1 の例: Jev が前後・左右・旋回の速度と 29 関節のオフセットを選び、歩容とバランスは Unitree の既存方策が受け持つ。

### ③ スキル選択

予測を担う部分がスキルの実装に含まれるため、前節の分担を自然に満たす。

- Askable Arm (ManiSkill の Franka): 約 30 個のプリミティブから 1 ステップに 1 つを選ばせ、トルクや軌道は出力させない。
- JEV control your roboarm (Isaac Sim): Jev を知覚と決定論的なスキルの間に置く意味的な判断層と位置づけ、ロボットのドライバが実行可能と確認済みの行動とパラメータだけを選択肢にしている。
- 実機では、SO-101 と USB カメラ 2 台で、毎秒約 2 回の判断によりボールをボウルに入れたデモがある。
- WidowX 実機の robojev は、紙コップ 1 個とテーブル 1 つに強く適合したデモだと作者自身が注記している。

### ④ 知覚判定

画像を Jev に渡す場合、行動を直接選ばせるより、画像についての単純な問いに答えさせ、その答えを古典的な制御則で行動に変える方がうまくいく。JEV-27B-VL のピックアンドプレースがこの形。Jev 1.14 の Box もこの層の候補だが、ロボットで使った公開事例は調査時点で見つからなかった。

### ⑤ 監視とゲート

- Jev_SO101: VLM の Astra が 2 視点の画像を解釈し、Jev がスキルを選ぶとともに「危険か」「完了したか」を判定する。
- シミュレーション上のヒューマノイドの例: Jev がタスクの区切りごとに確信度で次段階に進むかを判断し、実行は決定論的な物理ガードが管理する。
- 仮想ドローンの例: Jev が 99% の時間は単独で操縦し、確信度が低いときだけ大きなモデルに判断を譲った。

### ⑥ オフライン

ヒューマノイドの遠隔操作データに Jev を使い、42 秒の両腕作業を接近、把持、持ち上げ、移動、配置の 20 区間に分割した例がある。作者はサンプル数が最小限だと注記している。

## 活用方法による分類

Jev を他の部品とどう組み合わせるかで 7 通りに分ける。A から E は制御の構成そのもので、F と G は他の構成に重ねて使う。

| 方法 | 構成 | 評価と事例 |
| --- | --- | --- |
| A. 単独ポリシー | 毎ステップ Jev が行動を直接選ぶ | ②の層では動くが、予測が必要な判断で崩れる |
| B. 2 段階呼び出し | 1 回目で「何をするか」や「次に何が起きるか」を聞き、答えを state に書いて 2 回目で動作を選ぶ | 論文で精度の回復を確認。Dmytro Hrybov の MuJoCo の例、RoboJEV |
| C. コードが予測し Jev が評価 | 各選択肢の結果をコードやシミュレータで計算し、選択肢に添える | 効果が最も大きい。Stacker のスキル選択、ALFWorld の先読み |
| D. System 2 との階層 | LLM や VLM が計画や画像解釈を担い、Jev が高頻度の判断を担う | G1 と Gemini、SO-101 と Astra |
| E. 生成コード内の述語 | LLM がコードやハーネスを書き、その中の条件判定を Jev に任せる (Code as Policies 型) | JevHarness が先行例。ロボットでの定量評価は未確認 |
| F. 確信度による引き継ぎ | 確信度が低い判断だけを大きなモデルや人に回す | ドローンの例、エージェントハーネス全般 |
| G. 反射層との併用 | 高頻度で動く安全層が Jev の判断を拒否できる | ドローンの例では 50Hz の反射層が約 2.5Hz の Jev に拒否権を持つ |

- B と C は論文の診断に対する 2 つの対処にあたる。B は予測を Jev 自身の別の呼び出しに任せる方法で、Jev が入力から予測できる場合にだけ効く。ALFWorld で課題が「きれいなナイフを引き出しに入れる」のようにゴールだけを示す書き方のとき、Jev は次のサブゴールを 33% しか正しく答えられなかった。Jev が予測自体を誤る場合は、C のようにコードやシミュレータ、学習済みの世界モデル、より大きな推論モデルから予測を持ってくる必要がある、としている。
- E は Code as Policies の構成に Jev を組み込む形。Code as Policies では、LLM が自然言語の指示から、物体検出などの知覚 API を呼び、制御プリミティブ API にパラメータを渡す方策コードを書く。Jev は文章もコードも生成できないため、コードを書く役は LLM に残し、そのコードの中の分岐や終了判定を Jev が高速に評価する分担になる。NanoJev の作者が公開した JevHarness は、LLM にタスク専用の Jev 判断ハーネスを組ませ、報酬と実行トレースで改良する仕組みで、この形の直接の先行例とされている。

## 入力の作り方

Jev に何を見せるかで事例は 3 つに分かれ、実機への移しやすさが異なる。

- 特権状態: シミュレータが持つ物体位置や接触の真値を JSON で渡す。大半のデモがこの方法で、実機ではそのまま使えない。
- 知覚パイプラインの出力: 物体検出などの結果をテキストにしてから渡す。JEV control your roboarm は、シミュレータの真値を Jev に渡さない設計にしている。
- 画像を直接渡す: Jev 1.14 や JEV-27B-VL を使う。行動を直接選ばせず、少数択の問いに分解する使い方が前提になる。

## 具体例

### スキル選択: Stacker で新しい指示に従う

論文の Stacker の実験では、Jev に渡す state に、目標位置、手の位置、グリッパの状態、各箱の位置や「掴める状態か」「他の箱と近すぎるか」などをコードが計算して入れる。選択肢はそのときに実行可能なスキルだけで、`move_above_box`、`descend_to_box`、`close_gripper`、`lift`、`place_at_target` などがある。各スキルには、何をするかを書いた `what` と、使ってはいけない状況を書いた `not_for` が付く。たとえば `place_at_target` の `not_for` は「箱を持っていないとき、または目標が高い位置にあり下に支えがないとき」である。

この構成のまま指示文だけを「box0 を box1 の上に置け。目標マーカーは無関係」のように変えると、Jev は 40 エピソード中 22 で達成した。既定タスク用に書かれた手書きコントローラは指示を読めず、目標マーカーに箱を運んでしまうため 3 しか達成できなかった。スキルを既定タスク向けに作っておけば、指示の違いは Jev の評価が吸収するという結果だとしている。

### 知覚判定: 画像の二値判定によるピックアンドプレース

JEV-27B-VL のデモでは、上方カメラの画像を JEV-27B-VL に渡し、毎ステップ「目標はグリッパの左か右か」と「上か下か」の 2 つの二値の問いに答えさせる。アームは答えの方向へ一定量動き、答えが前回と反転したら移動量を半分にする。MuJoCo のランダムな 20 シーンで 75% を達成し、掴めた立方体はすべてトレイに入った。失敗はすべて、狙いから 3.0〜3.7cm ずれた把持だった。判断 1 回は約 240ms。

資料はこの制御則の働きを、1 軸だけの仮の値で示している (グリッパの初期位置 0、目標 0.13、初期の移動量 0.08。反転時に先に移動量を半分にしてから動く順序も説明のための仮定)。ステップ 1 は「右」で 0.08 動いて位置 0.08、ステップ 2 は「右」で位置 0.16、ステップ 3 は「左」に反転して移動量 0.04 で位置 0.12、ステップ 4 は「右」に反転して移動量 0.02 で位置 0.14、ステップ 5 は「左」に反転して移動量 0.01 で位置 0.13 になる。モデルが答えるのは毎回「左か右か」だけで、位置の数値は一度も出力しない。数値の精度が必要な部分は制御則が受け持つため、Jev の苦手な数値の精度と得意な評価が分離されている、としている。

### 生成コード内の述語: Code as Policies との組み合わせ

Code as Policies の生成コードに Jev を組み込む場合の形を、仮の例で示している。資料は「動作を確認していない説明用のコード」と断っている。`jev_noul` と `jev_choice` は Jev の API を呼んで確率を返す関数、`detect_objects`、`pick`、`place` は既存の知覚 API と制御プリミティブ API を想定している。

```python
# LLM が「床の靴下を全部カゴに入れて」から生成する方策コードの例（仮）
objs = detect_objects(camera.capture())
for obj in objs:
    # 物体が靴下かどうかの判定を Jev に任せる
    if jev_noul(state={"crop": obj.crop, "label": obj.label},
                question="この物体は靴下か") < 0.7:
        continue
    pick(obj.pose)
    # 把持の成否も Jev が画像で判定し、失敗なら 1 回だけやり直す
    if jev_noul(state={"wrist_image": wrist_cam.capture()},
                question="グリッパは物体を保持しているか") < 0.5:
        pick(obj.pose)
    place(basket.pose)
```

この例で Jev が答えるのは、どれも入力の画像だけで判断できる評価の問いである。「この把持で持ち上げたら落ちるか」のような、実行後の物理状態の予測が必要な問いは論文の境界の外側にあたり、そうした判断は生成コード側で試行して結果を確認する形にした方が既存の知見と整合する、としている。

## オープンモデル

Jev の公開から数日で、同じ入出力の形式を持つオープンモデルが多数現れた。ロボットや制御に関係するものは次の 2 つ。

- JEV-27B-VL (AutoTrust、Apache-2.0、https://huggingface.co/autotrust/JEV-27B-VL): Qwen3.8-27B に判断用のアダプタとヘッドを足したモデル。判断ヘッドはテキストだけで学習しており、画像に対する判断はすべてゼロショット。ピックアンドプレース 75%、ERQA (身体性推論のベンチマーク) は推論なしで 53.8%。80GB 以上の GPU で動かす。Jev 1.13 の出力分布を蒸留しており、6 種の判断ベンチマークの平均では Jev 1.13 と同水準と自ら報告している。
- NanoJev (MIT、https://github.com/TianyuCodings/NanoJev/wiki): Qwen3-0.6B に判断ヘッドを足した小型モデル。ViZDoom Basic で 128/128 を達成し、Jev の 56/128 を上回った。ただし評価と同じ 4 つのゲームで学習しており、汎用の判断モデルではない。

汎用の判断精度ではまだ Jev とオープンモデルに差があり、49 タスクの独立ベンチマークでは Jev の 0.966 に対し最良のオープンモデルは 0.704 だった。

## 限界と注意

- 数値の多くは 1 シードの単発デモか、ベンダーやモデル作者自身による評価である。査読前の論文を含めても、複数の構成を同じ条件で比べた定量研究は Yang らの論文だけで、その論文も Jev 1 バージョンのみを扱っている。
- 同じリクエストを繰り返すだけで、Jev の返す確率は平均 0.04 変わり、選ばれる選択肢は 12% のケースで変わる。選択肢の並び順でも確率が変わるため、論文では複数の並び順で平均を取っている。資料は、制御ループで使う場合も重要な判断では並び順を変えた複数回の呼び出しを検討する価値があるとしている。
- ネットワーク越しに呼ぶ API は、中央値が速くても毎周期の締め切りを保証できないため、ハードリアルタイムの制御には使えない。この指摘は独立サイト systemonemodels.org のリアルタイム制御のページにある。資料は、バランスや衝突回避のような反射的な制御は歩行の例のように既存の方策や反射層に任せ、Jev はその上の層に置くのが現実的だとしている。
- 画像入力は公開から 11 日しか経っておらず、Jev 1.14 の画像機能をロボットに使った公開事例は調査時点で見つからなかった。Box が対象の不在を返さない仕様は、物体の有無を Noul で先に確かめてから位置を聞くといった手順で補う必要がある、としている。

## 用語

資料末尾の用語集の定義。

- System 1 モデル: 文章を生成せず、定義済みの選択肢や尺度に対する確率を 1 回の計算で返すモデル
- 評価: 入力と選択肢に含まれる情報だけで正解を判断できる判断
- シミュレーション: 相手の行動や行動後の状態など、入力にない予測を経なければ正解が決まらない判断
- スキル: 「箱の上へ移動」「持ち上げる」のように、コードが IK や PD 制御で実装した一連の動作
- 動作プリミティブ: 移動方向やグリッパの開閉など、スキルより細かい単位の動作
- 特権状態: シミュレータが持つ物体位置や接触などの真値。実機では直接得られない
- 先読み: 各候補の行動を環境のコピーで実行し、結果を選択肢に添えておく処理
- VLA: Vision-Language-Action モデル。画像と指示から行動を直接出力する学習済みポリシー
- Code as Policies: LLM が自然言語の指示から、知覚 API と制御 API を呼ぶロボットの方策コードを書く手法
